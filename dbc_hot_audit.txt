SSF DBC CHECKS IN HOT CODE: REDUNDANT OR IMPOSSIBLE ASSERTIONS
==============================================================
Audit date : 2026-11-27
Scope      : SSF_REQUIRE / SSF_ASSERT / SSF_ENSURE checks inside the functions that dominate
             run time, and whether removing redundant or impossible ones is worth it.
             Code at commit 6389bda (branch mqtt).
Status     : items A, B, C implemented (see RESULTS); everything else is KEEP by measurement.

SUMMARY
-------
  - Every hot check costs little. Removing all checks in SSF (upper bound) makes no measured
    operation more than 0.8% faster, and it makes RSA 8.6-9.1% and P-256/P-384 0.5-3.9% SLOWER.
  - SSFPortAssert is noreturn, so after a check passes the compiler may assume it holds
    (e.g. "n <= SSF_BN_MAX_MOD_LIMBS" proves that uint16_t loop indices cannot wrap). Several
    redundant checks therefore make the code faster and must stay.
  - Three groups have a measurable cost and are removed: A (ssffe25519), B (SSFBNMul on the
    NIST fast path), C (the AES block function on the GCM / CCM / CTR paths).

METHOD
------
Profile : the 12 benchmark operations of bnzero_report.txt run under qemu-arm with
          -d in_asm,exec,nochain; executed instructions summed per function. Functions with
          >= 1% of an operation's instructions are "hot": 41 functions, 30 with checks
          (about 190 checks).
Removal : a scratch tree per function group in which the group's checks become
          "(void)(x)" (the expression is still evaluated: some library asserts have side
          effects, e.g. SSF_ASSERT(SSFBNFromBytes(...)) in ssfecdsa.c). Unit tests off.
Counts  : arm-linux-gnueabihf-gcc 14, -mthumb -march=armv7-a+fp -Os, static; setup work
          subtracted as in bnzero_report.txt.

ALL CHECKS REMOVED (upper bound)
--------------------------------
  RSA-2048 sign / verify           8.6% / 9.1% SLOWER
  P-256 / P-384                    0.5 - 3.9% SLOWER
  X25519, Ed25519                  0.4 - 0.8% faster
  AES-GCM/CCM, SHA-2, ChaCha20-Poly1305   0.01 - 0.7% faster

DECISIONS
---------
  KEEP  _SSFBNRawAdd/RawSub/RawCmp, SSFBNCondCopy, SSFBNMontSquare: redundant but they speed
        the code up. Do not remove them in a future audit.
  KEEP  SSF_ASSERT(e == 0) in the NIST reductions: one compare per reduction, guards a real
        math invariant.
  KEEP  SSFBNMontMul, the NIST reductions, _SSFBNNistFold, SHA/Poly1305 update: each saves
        under ~0.5% and only on some operations; not worth the churn.
  DONE  A, B, C below. Each removal site carries a comment pointing here, so the checks are
        not added back.

ITEMS DONE
----------
  A  ssffe25519 (internal module, header says "not a public API"): no argument checks in
     SSFFE25519Mul, Sqr, Reduce, CSwap, Copy. Their SSF_ASSERT_TEST contract tests removed.
     Inv, ToBytes, SetZero, SetOne keep theirs (not hot).
  B  ssfbn: SSFBNMul's body moved to static _SSFBNMulCore. SSFBNMul keeps all 14 checks.
     _SSFBNModMulNISTFast calls the core directly and keeps only a->len <= a->cap and
     b->len <= b->cap, the two facts its callers do not establish.
  C  ssfaes: new _SSFAESKSBlockEncryptNoCheck() for the ssfaes* modes. GCTR (GCM), CCM and
     CTR call it per block; SSFAESKSBlockEncrypt keeps its checks for external callers.
     _SSFAESGCMMulH (static, called per block by _SSFAESGCMAbsorb, which checks the same
     pointers) drops its two NULL checks.

OTHER FINDINGS (not DBC checks)
-------------------------------
  - SSFCryptSecureZero is 8.6% of SHA-256 and 6.2% of SHA-384 (each block wipes its 256-byte
    message schedule), 4.2% of ChaCha20-Poly1305 and 2-3% of AES-GCM/CCM. This buys secret
    hygiene; changing it is a security trade-off, not a cleanup.
  - Some library asserts do work inside the check (ssfecdsa.c:189, ssfjson.c:746, ssfsm.c:277,
    ssfnetws.c:106/613, ssflptask_opt.h). Fine while asserts are always on; any future assert
    mode (codesize_audit.txt #2) must still evaluate the expression.
