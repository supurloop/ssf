1. FINDINGS CHECKED AGAINST AWS DOCS
=====================================================================================================

1.1 TLS 1.3: SUPPORTED, AND ON BY DEFAULT FOR NEW ENDPOINTS
  - "AWS IoT Core supports the following versions of the TLS protocol: TLS 1.3, TLS 1.2." [TS]
  - "The default predefined security policy for non-AWS GovCloud (US) regions is
    IoTSecurityPolicy_TLS13_1_2_2022_10." It allows TLS 1.2 and TLS 1.3. [TS]
  - "If you create a new domain configuration, the security policy will default to
    IoTSecurityPolicy_TLS13_1_2_2022_10 for all regions excluding AWS GovCloud (US)." [TLS]
  - GovCloud default is IoTSecurityPolicy_TLS13_1_2_2022_01 (TLS 1.2 + 1.3, AES-GCM only). [TS]
  - Other policies that allow TLS 1.3: IoTSecurityPolicy_TLS13_1_3_2022_10 (TLS 1.3 only). [TS]
  - Policies with NO TLS 1.3: IoTSecurityPolicy_TLS12_1_2_2022_10, _TLS12_1_0_2016_01,
    _TLS12_1_0_2015_01. [TS]
  - NOT DOCUMENTED: which policy the existing iot:Data-ATS endpoint of an older account uses.
    It can be read and changed:
        aws iot describe-domain-configuration --domain-configuration-name "iot:Data-ATS"
        aws iot update-domain-configuration --domain-configuration-name "iot:Data-ATS" \
            --tls-config securityPolicy=IoTSecurityPolicy_TLS13_1_2_2022_10          [TLS]
    Custom security policies are not supported. [TLS]
  Consequence: ssftlsc (TLS 1.3 only) works against the default endpoint configuration. An
  account whose iot:Data-ATS still uses a TLS12_* policy needs one update-domain-configuration
  call. ssfawsprov.md must say so (task M09), and V01 checks it on a real account.

1.2 TLS PARAMETERS MATCH WHAT ssftlsc OFFERS
  - TLS 1.3 suites in the 2022_10 policies: TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384,
    TLS_CHACHA20_POLY1305_SHA256. [TS] ssftlsc offers ChaCha20-Poly1305, AES-128-GCM,
    AES-256-GCM, AES-128-CCM (_net/ssftlsc.c:813). There is overlap on all three AWS suites.
  - Server roots: Amazon Root CA 1 (RSA 2048) and Amazon Root CA 3 (ECC P-256); CA 2 (RSA 4096)
    and CA 4 (ECC P-384) are "reserved for future use". All cross-signed by Starfield. The chain
    served depends on the endpoint type and the negotiated suite. [SA] The app should trust CA 1
    and CA 3 (and may add CA 2 / CA 4). ssfx509 verifies both key types.
  - Client keys: RSA >= 2048, ECC P-256 / P-384 / P-521, RSA-PSS (TLS 1.3 only). [XC]
    ssftlsc signs CertificateVerify with P-256, P-384, Ed25519 or RSA-PSS: P-256 and P-384 fit.
  - Supported key-exchange groups: not documented. ssftlsc offers x25519, P-256, P-384. V01
    records which one is negotiated.
  - SNI: [TS] says "not required but highly recommended", and required for custom domains,
    configured TLS policies and multi-account registration; [XC] and [JIT] say the device is
    required to send it. ssftlsc always sends SNI for a host name. No change needed.
  - ALPN: MQTT with an X.509 client certificate on port 443 must offer ALPN "x-amzn-mqtt-ca";
    port 8883 needs no ALPN. [PR] SSFTLSCSetALPN() exists; the name (14 bytes + 1 length byte)
    fits SSF_TLS_CONFIG_MAX_ALPN_LEN (32).

1.3 MQTT LIMITS [Q]
  - Client ID: 128 bytes UTF-8, not adjustable. ssfmqttc default was 64 (incl. NUL): too
    small for clientId = thingName. G05 raises it to 129.
  - Thing name: 128 bytes UTF-8, not adjustable.
  - Keep-alive: requests in 1..29 s are treated as 30 s; 0 or > 1200 gets 1200 s. ssfmqttc
    requires keepAliveSec >= 120 with its 30 s PINGRESP timeout. Use 120..1200.
  - Payload: 128 KB per publish. Topic: 256 bytes, at most 7 '/'. Subscriptions: 50 per
    connection. Publish: 100 per second per connection.
  - Fleet provisioning throttles (account-wide, adjustable): CreateCertificateFromCsr 20 TPS,
    CreateKeysAndCertificate 10 TPS, RegisterThing 10 TPS. A fleet coming up together will be
    throttled: retry with backoff and jitter (M07).

1.4 FLEET PROVISIONING MQTT API [FPA]
  - Topics ({fmt} is json or cbor):
        $aws/certificates/create-from-csr/{fmt}                 request
        $aws/certificates/create-from-csr/{fmt}/accepted        response
        $aws/certificates/create-from-csr/{fmt}/rejected        error
        $aws/provisioning-templates/{templateName}/provision/{fmt}             request
        $aws/provisioning-templates/{templateName}/provision/{fmt}/accepted    response
        $aws/provisioning-templates/{templateName}/provision/{fmt}/rejected    error
    (CreateKeysAndCertificate: $aws/certificates/create/{fmt}[/accepted|/rejected], empty
    request payload. Not used; see section 5.)
  - CreateCertificateFromCsr request : {"certificateSigningRequest": "<CSR in PEM>"}
    response: {"certificateOwnershipToken": "...", "certificateId": "...",
               "certificatePem": "..."}
  - RegisterThing request : {"certificateOwnershipToken": "...",
                             "parameters": {"string": "string", ...}}     (parameters optional)
    response: {"deviceConfiguration": {"string": "string", ...}, "thingName": "..."}
  - Error, all operations: {"statusCode": int, "errorCode": "string", "errorMessage": "string"}.
    No error codes are listed.
  - "Before publishing a request message topic, subscribe to the response topics." Results come
    back on the same MQTT connection. QoS and wildcard subscriptions are not covered: use QoS 1
    and the four exact filters.
  - The ownership token "expires after one hour"; RegisterThing must be called before then.
    The new certificate is PENDING_ACTIVATION until RegisterThing, then ACTIVE or INACTIVE per
    the template. If it is not activated before the token expires, AWS deletes it, and the
    device can simply call CreateCertificateFromCsr again. A repeated CSR therefore leaves no
    permanent orphan certificate.
  - Template name: 1..36 characters, pattern ^[0-9A-Za-z_-]+$. [API] Longest topic is then
    28 + 36 + 24 = 88 bytes with 5 '/': fits SSF_MQTTC_CONFIG_MAX_TOPIC_SIZE (257) and [Q].
  - CSR key: RSA >= 2048 or ECC P-256 / P-384 / P-521 [XC]. The API page sets no subject rules.

1.5 CLAIM CERTIFICATES [PWC]
  - By claim: a shared claim certificate with an IoT policy. The documented example policy
    allows $aws/certificates/create/* and $aws/provisioning-templates/<name>/provision/*. That
    wildcard does NOT match create-from-csr; the policy for this module must name
    $aws/certificates/create-from-csr/* (Publish, Receive) and the matching topicfilter
    (Subscribe). ssfawsprov.md must show the corrected policy (M09).
  - By trusted user: an app calls CreateProvisioningClaim and gives the device a temporary claim
    certificate that "expires after five minutes"; the device must finish provisioning within
    five minutes of connecting with it. Same MQTT flow, shorter deadline (M07).
  - Pre-provisioning hooks (Lambda) see the RegisterThing parameters; nothing device-side.

1.6 JITP (NO MODULE NEEDED) [JIT]
  The device connects with a certificate signed by a registered CA that has a JITP template;
  sending the CA certificate is optional, SNI is required. AWS runs RegisterThing itself. With
  ssftlsc this is just SSFTLSCSetClientCert() with a one- or two-certificate chain. Document it
  in ssfawsprov.md; no code.

1.7 STILL UNVERIFIED (settled by V01..V03)
  - Real response sizes, especially the ownership token length. The estimate below drives G04.
  - Which iot:Data-ATS policy a given existing account has.
  - Whether AWS accepts wildcard subscriptions on these topics (not needed by this plan).

1.8 SIZE ESTIMATE FOR THE CreateCertificateFromCsr RESPONSE
  certificatePem ~1.2 KB (escaped "\n" adds ~20 bytes) + certificateId 64 + token several
  hundred bytes to ~1 KB + keys and punctuation ~100 => ~2.1..2.5 KB. This exceeds
  SSF_JSON_CONFIG_MAX_IN_LEN (2047). V02 measures it.

AWSPROV-G01  ssfpem: PEM encoder
  Why    : The CSR travels as PEM text inside JSON. ssfpem only decodes (SSFPEMDecodeNext).
           Output must be byte-identical to OpenSSL's and must decode with SSFPEMDecodeNext.

  API (_codec/ssfpem.h)
    /* Bytes SSFPEMEncode() writes, NUL included: 2L + 32 + 4*ceil(n/3) + ceil(n/48) + 1.     */
    #define SSF_PEM_ENCODE_SIZE(labelLen, derLen) \
        ((2u * (labelLen)) + 33u + (4u * (((derLen) + 2u) / 3u)) + (((derLen) + 47u) / 48u))

    bool SSFPEMEncode(const char *label, const uint8_t *derOpt, size_t derLen,
                      char *pemOpt, size_t pemSize, size_t *pemLenOut);

  Output : "-----BEGIN <label>-----\n", Base64 at 64 characters (48 input bytes) per line, each
           line ending "\n", "-----END <label>-----\n", then NUL. This is OpenSSL's layout. Empty
           DER gives the two lines only, which the decoder already accepts (ssfpem_ut.c:155).

  Behavior
    - *pemLenOut is always set to the length needed (NUL not counted), including when the
      call fails for size, so a caller can size a buffer. pemOpt NULL measures, returns true.
    - pemSize < need + 1: returns false and zeroes all pemSize bytes of pemOpt (the block may
      hold a private key; same policy as the decoder's fail path). Nothing beyond pemSize is
      touched. The size is checked before writing, so no partial block is ever visible.
    - SSF_REQUIRE (programming errors): label or pemLenOut NULL; derOpt NULL with derLen > 0;
      derLen > SIZE_MAX / 2 (keeps the length formula from overflowing); pemOpt overlapping
      derOpt; an invalid label.
    - Label rules match the decoder exactly, so every label the decoder returns re-encodes,
      and every label the encoder accepts decodes back:
        * 1..SSF_PEM_MAX_LABEL_LEN (40) characters;
        * each character 0x20..0x7E;
        * no "-----" anywhere in it (the decoder ends the label at the first "-----");
        * last character not '-' (it would merge with the closing dashes; the decoder then
          rejects the BEGIN line, so it never returns such a label).
      Leading, trailing and repeated spaces are allowed, as in the decoder. RFC 7468 is
      stricter (no leading/trailing/double space or '-'); conforming output is the caller's
      choice of label. A bad label can only come from a coding error (labels are literals at
      every planned call site), hence REQUIRE rather than a false return.

  Implementation (_codec/ssfpem.c, about 70 lines)
    1. static _SSFPEMLabelIsValid(label, &labelLen): one pass applying the rules above.
    2. need = formula above; *pemLenOut = need; if pemOpt == NULL return true.
    3. If pemSize < need + 1: SSFCryptSecureZero(pemOpt, pemSize) when pemSize > 0; false.
    4. memcpy the BEGIN line; for each chunk of up to 48 bytes, SSFBase64Encode(chunk, c,
       &pem[w], 65, &n) (writes <= 64 chars + NUL) and overwrite the NUL with '\n'; memcpy the
       END line; NUL.
    5. SSF_ASSERT(w == need).
    Uses only the public SSFBase64Encode (SSFBase64Enc24To32 is not in ssfbase64.h). No
    scratch buffer to wipe: Base64 goes straight to the caller's buffer. ssfpem.c already
    includes ssfbase64.h and ssfcrypt.h, so no build changes.

  Tests (_codec/ssfpem_ut.c, new "---- Encode ----" sections)
    1. Known vectors: {0,1,2,3}, "TEST" => exactly
       "-----BEGIN TEST-----\nAAECAw==\n-----END TEST-----\n"; empty DER, "EMPTY" => exactly
       "-----BEGIN EMPTY-----\n-----END EMPTY-----\n" (the decoder tests' own strings).
    2. Line boundaries, n = 1, 2, 3, 45, 46, 47, 48, 49, 95, 96, 97, 144: every body line but
       the last is 64 characters; the last is 4*ceil(r/3) where r is the bytes left for it;
       no blank line when n % 48 == 0; "=" / "==" padding exactly when n % 3 is 2 / 1.
    3. Round trip, every n in 0..300 with a fixed byte pattern: encode, then SSFPEMDecodeNext
       gives SSF_PEM_BLOCK, the same label and bytes, pos == encoded length; the returned
       length == strlen(output) == SSF_PEM_ENCODE_SIZE(L, n) - 1.
    4. OpenSSL byte-exact: embed one OpenSSL-made certificate PEM (3+ lines, padded last
       line) and one CERTIFICATE REQUEST PEM (reused by G03); decode, re-encode, memcmp with
       the original text. A comment records the openssl command that made each.
    5. Measure mode: pemOpt NULL returns true and the same *pemLenOut as a real encode;
       char buf[SSF_PEM_ENCODE_SIZE(11u, 900u)] compiles (array size) and fits exactly.
    6. Buffer sizes, using a buffer filled with a marker byte: pemSize = need (no room for
       NUL), 1, and 0 each return false with *pemLenOut == need, bytes [0, pemSize) zero,
       bytes past pemSize still the marker; pemSize = need + 1 succeeds.
    7. Labels, accepted and round-tripped: "X", "CERTIFICATE", "CERTIFICATE REQUEST", "A-B",
       "A----B", "EC PRIVATE KEY", " X", "X ", "A  B", a 40-character label. Also: every
       label the decoder accepts in the existing decoder tests re-encodes and decodes back.
       Refused with SSF_ASSERT_TEST (as ssfbase64_ut.c:143): "", 41 characters, "A-",
       "A-----B", "-----", '\t', '\n', 0x7F, 0x80.
    8. REQUIRE: SSF_ASSERT_TEST on NULL label, NULL pemLenOut, NULL derOpt with derLen 1,
       derLen SIZE_MAX / 2 + 1, overlapping buffers; NULL derOpt with derLen 0 succeeds.

  Docs   : ssfpem.h header comment "block decoder" -> "block encoder and decoder"; ssfpem.md
           retitled "PEM Block Codec" (renames the [↑] anchors), SSFPEMEncode and
           SSF_PEM_ENCODE_SIZE added to API Summary and Function Reference with an example,
           note on output format and label rules; _codec/README.md row -> "PEM (RFC 7468)
           block encoder and decoder".
  Done   : ./ssf passes on Linux and with build-asan.ninja; tools/coverage shows 100% of the
           new lines; ARM and XC32 builds have no new warnings; tools/config-matrix
           features.sh passes. One commit: ssfpem.{h,c,md}, ssfpem_ut.c, _codec/README.md.

AWSPROV-G02  ssfpkey: build a key from a raw EC scalar
  Why    : SSFTLSCSetClientCert() only takes an SSFPKey_t from SSFPKeyDecodeDER/PEM. The device
           generates its key with SSFECDSAKeyGen and should store only the 32/48-byte scalar,
           rebuilding the SSFPKey_t at boot without a DER round trip. The result must be
           identical to what SSFPKeyDecodeDER returns for the same key; ssftlsc relies on it.

  API (_codec/ssfpkey.h)
    /* Builds a P-256 / P-384 key from its raw big-endian scalar; derives and sets pub. */
    bool SSFPKeyFromECPriv(SSFPKeyType_t type, const uint8_t *priv, size_t privLen,
                           SSFPKey_t *keyOut);

  Behavior
    - SSF_REQUIRE (programming errors), matching the ssfecdsa raw-scalar API
      (SSFECDSAPubKeyFromPrivKey, SSFECDSASign, SSFECDHComputeSecret all REQUIRE
      privKeyLen == c->bytes):
        * priv or keyOut NULL;
        * type not SSF_PKEY_TYPE_P256 / SSF_PKEY_TYPE_P384 (NONE, RSA, ED25519, MIN, MAX);
        * privLen != the curve size (32 for P-256, 48 for P-384). No short-scalar padding:
          SSFECDSAKeyGen always writes full width, and padding would turn a truncated record
          into a different valid key. The caller must validate any stored length first;
          ssfpkey.md says so.
        * priv overlapping *keyOut (keyOut is wiped before priv is read).
    - Returns false, *keyOut wiped to type NONE (data errors):
        * scalar outside [1, n-1]: 0, n, n+1, all 0xFF;
        * curve compiled out (SSF_EC_CONFIG_ENABLE_P256/P384 == 0), as the decoders do. The
          check precedes the curve-size REQUIRE, since the size is unknown for a disabled
          curve, and precedes SSFECDSAPubKeyFromPrivKey, which REQUIREs an enabled curve.
    - Success: *keyOut is byte-identical to an SSFPKeyDecodeDER of the same key's SEC1 DER:
      type set, priv[0..privLen) the scalar, privLen 32/48, pub the uncompressed point,
      pubLen 65/97, rsaDer NULL, rsaDerLen 0, every unused byte zero.
    - Cost: one fixed-base scalar multiplication (about one key generation). Once per boot or
      connection setup; documented.

  Implementation (_codec/ssfpkey.c, about 35 lines)
    1. REQUIRE priv, keyOut non-NULL, type P256/P384, no overlap (uintptr_t checks as in
       ssfpem); SSFPKeyWipe(keyOut).
    2. Select curve from type under #if SSF_EC_CONFIG_ENABLE_*; a compiled-out curve returns
       false. size = 32 or 48; REQUIRE(privLen == size).
    3. memcpy(keyOut->priv, priv, size); SSFECDSAPubKeyFromPrivKey(curve, keyOut->priv, size,
       keyOut->pub, sizeof(keyOut->pub), &keyOut->pubLen) checks 1 <= d <= n-1 and derives
       pub (the same call _SSFPKeyDecodeSEC1 makes).
    4. Failure: SSFPKeyWipe(keyOut), return false. Success: privLen = size, type set last.

  Tests (_codec/ssfpkey_ut.c, new "---- FromECPriv ----" section; reuse _UTCheckEC)
    1. Equivalence: FromECPriv(P256, _pkP256Priv, 32) equals DecodeDER(_pkP256SEC1Der) field
       by field and by memcmp of the whole struct; pub equals _pkP256Pub. Same for P-384 with
       _pkP384Priv / _pkP384SEC1Der / _pkP384Pub.
    2. Stale contents: keyOut pre-filled with 0xAA; after success the unused tails of priv and
       pub are zero and rsaDer / rsaDerLen are NULL / 0.
    3. Scalar edges, each curve (needs a new _utP384N beside _utP256N): 1, n-1 and a scalar
       with a leading 0x00 byte succeed; 0, n, n+1, all 0xFF return false and leave the whole
       struct zero.
    4. Failure wipes a valid key: a struct holding a good key, called again with scalar 0,
       comes back all zero.
    5. Generated keys: SSFECDSAKeyGen then FromECPriv gives pub equal to the KeyGen output;
       when signing is built, SSFECDSASign with key.priv verifies against key.pub.
    6. Compiled out: under SSF_EC_CONFIG_ENABLE_P256 == 0 a P-256 call returns false and wipes
       (any privLen, since the size check is not reached); same for P-384. Run by the
       config-matrix p256off / p384off rows.
    7. REQUIRE (SSF_ASSERT_TEST): NULL priv; NULL keyOut; type NONE, RSA, ED25519,
       SSF_PKEY_TYPE_MIN, SSF_PKEY_TYPE_MAX; privLen 0, 31, 33, 48 for P-256 and 0, 32, 47,
       49 for P-384; priv inside keyOut->priv; priv overlapping the first or last byte of
       *keyOut. priv directly adjacent to *keyOut succeeds.
    8. TLS (_net/ssftlsc_ut.c, SSFTLSCSetClientCert section): DecodeDER(_utClientP256Key),
       rebuild with FromECPriv(P256, key.priv, key.privLen); SetClientCert accepts it with
       _utClientP256Cert and refuses it with _utClientOtherCert. Same for P-384 with
       _utClientP384Key / _utClientP384Cert.

  Docs   : ssfpkey.md: function reference and example (KeyGen, store the scalar, rebuild at
           boot, SetClientCert); what returns false vs what is REQUIRE, including "validate a
           stored length before calling"; the scalar-multiplication cost. _net/README.md (where
           ssftlsc is documented): the SetClientCert key note adds SSFPKeyFromECPriv(). README
           and _codec/README.md: ssfpkey row and size figure measured on Cortex-M4.
  Done   : ./ssf passes on Linux and with build-asan.ninja; tools/coverage shows 100% of the
           new lines; tools/config-matrix features.sh passes (p256off, p384off, signoff rows);
           ARM and XC32 builds have no new warnings. One commit, TDD: ssfpkey.{h,c,md},
           ssfpkey_ut.c, ssftlsc_ut.c, _net/README.md, _codec/README.md, README.md.
  Note   : Pre-existing, found while planning: SSFECDSAPubKeyFromPrivKey returns early on an
           invalid scalar without zeroizing its local copy d. Tracked as AWSPROV-G08.

AWSPROV-G03  ssfx509: PKCS#10 CSR encoder
  Why    : CreateCertificateFromCsr needs the device's CSR (RFC 2986) as PEM. ssfx509 encodes
           certificates but not CSRs. As for certificates, signing stays outside ssfx509: one
           call encodes what is signed, the caller signs it, a second call wraps the signature.

  Checked (OpenSSL 4.0.3, 2026-11-26)
    - "openssl req -new -sha256 -sigopt nonce-type:1" signs deterministically (RFC 6979):
      two runs are identical. SSFECDSASign is RFC 6979 and does not normalize s, so whole
      CSRs, signature included, should match OpenSSL byte for byte.
    - Layout: SEQ { SEQ { INTEGER 0, Name, SPKI, [0] {} }, SEQ { ecdsa-with-SHA256 },
      BIT STRING }. Attributes are an empty A0 00; the signature AlgorithmIdentifier has no
      parameters (as _SSFX509EncAlgId writes); strings are UTF8String except C
      (PrintableString), as _SSFX509EncDNAttr writes.
    - An empty subject ("-subj /") encodes as 30 00 and verifies; _SSFX509EncDN writes that
      when every name field is NULL.
    - SSF enforces ub-common-name = 64 (RFC 5280); AWS thing names are up to 128 bytes, so
      M03 must not put a long thing name in CN. Whether AWS accepts an empty subject is
      unverified: V02 checks it.

  API (_codec/ssfx509.h)
    typedef struct SSFX509CSRParams
    {
        SSFX509GenName_t subject;       /* All NULL gives an empty subject */
        const uint8_t *sigAlgOidRaw;    /* ecdsa-with-SHA256 / SHA384 (raw DER content) */
        uint32_t sigAlgOidRawLen;
        const uint8_t *pubKeyAlgOidRaw; /* id-ecPublicKey */
        uint32_t pubKeyAlgOidRawLen;
        const uint8_t *ecCurveOidRaw;   /* prime256v1 / secp384r1 */
        uint32_t ecCurveOidRawLen;
        const uint8_t *pubKey;          /* Uncompressed point, e.g. SSFPKey_t.pub */
        uint32_t pubKeyLen;
    } SSFX509CSRParams_t;

    bool SSFX509EncodeCSRInfo(uint8_t *bufOpt, uint32_t bufOptSize,
                              const SSFX509CSRParams_t *params, uint32_t *lenOut);
    bool SSFX509EncodeCSR(uint8_t *bufOpt, uint32_t bufOptSize, const SSFX509CSRParams_t *params,
                          const uint8_t *signature, uint32_t signatureLen, uint32_t *lenOut);
    Raw OIDs, as in SSFX509GenParams_t (no ssfx509 -> ssfpkey dependency); M03 supplies them.

  Behavior (mirrors EncodeTBS / EncodeCert)
    - Measure-then-write: bufOpt NULL returns true with *lenOut = size. On failure *lenOut
      is 0 and false is returned: a subject field over its RFC 5280 bound, C not two
      PrintableString letters, total over SSF_X509_CONFIG_MAX_CERT_SIZE, buffer too small.
      A CSR is public: a failed buffer is not zeroed (same policy as certificates).
    - SSF_REQUIRE: params / lenOut NULL; bufOpt NULL with a size; any OID or pubKey NULL or
      length 0; ecCurveOidRaw NULL (EC keys only: the SPKI encoder gives a non-EC key a bare
      AlgorithmIdentifier, which is wrong for RSA); signature NULL or signatureLen 0; bufOpt
      overlapping signature or params->pubKey (added in the audit: an overlapping key would
      be overwritten before it is copied, silently corrupting the CSR).
    - signature is the DER ECDSA-Sig-Value from SSFECDSASign, wrapped in a BIT STRING with 0
      unused bits, not checked (as EncodeCert).

  Implementation (_codec/ssfx509.c, about 100 lines; certificate paths unchanged)
    1. _SSFX509EncCRIContent: INTEGER 0 (_SSFX509EncIntU64), _SSFX509EncDN(&subject), SPKI
       (a zeroed local SSFX509GenParams_t holding only the four public-key fields, through
       _SSFX509EncSPKIContent in a SEQUENCE), then A0 00 (_SSFX509EncTagLen).
    2. _SSFX509EncCSRContent: CRI, _SSFX509EncAlgId(sigAlg), _SSFX509EncBitString(sig).

=====================================================================================================
5. OUT OF SCOPE / DEFERRED
=====================================================================================================
  - CreateKeysAndCertificate: AWS generates the key and returns it in the response (~4 KB),
    so the private key crosses the network. The CSR path is preferred.
  - CBOR payload format: SSF has no CBOR codec; JSON is enough.
  - RSA device keys and RSA CSRs: P-256 / P-384 cover AWS [XC] and are far cheaper on small
    cores. Can be added to G03 later.
  - JITP / JITR: no device protocol beyond mutual TLS (1.6). Documentation only.
  - Certificate rotation after provisioning (AWS IoT Device Defender / Jobs): separate module.
  - MQTT 5 and custom authentication (ALPN "mqtt"): not supported by ssfmqttc.
