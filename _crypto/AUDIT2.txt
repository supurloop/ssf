PRNG-3  Low  OPEN  [code-read]
  Location:  ssfprng.c:56-66 (SSFPRNGInitContext / SSFPRNGReInitContext alias); ssfprng.md:67
  Problem:   "Re-seed" replaces the key with the new entropy instead of mixing it into the
             current state (SP 800-90A reseed combines old state and new input). A reseed with
             weak or attacker-influenced entropy therefore throws away whatever good state the
             context had.
  Failure:   A device that periodically reseeds from a source that occasionally returns low
             entropy (e.g. a stuck TRNG) loses the strength of earlier good seeds.
  Options:   (1) Make ReInit derive key' = AES_key(entropy-derived blocks) XOR-combined with the
             current key (keep Init as replace). (2) Document that ReInit is a replace and
             callers must supply full-strength entropy.  Recommend (2) unless a mixing reseed
             is wanted; (1) changes output streams.

  Verified correct: per-call re-key (backtracking resistance), domain separators 0x00/0x01/
  0x02, big-endian counter, effective key size forced to 256 bits for P-384 / RSA-4096,
  stack scrub of pt/ct/newKey.

  Location:  ssfaesgcm.c:382-449 (SSFAESGCMEncrypt), :454-535 (SSFAESGCMDecrypt) locals h, s, j0,

  Options:   (1) SSFCryptSecureZero h, s, j0, j1, buf before every return of Encrypt/Decrypt

BN-10  Medium  OPEN  [measured]
  Location:  ssfbn.c:1937-1972 (SSFBNModInv; verification at :1965-1969); ssfbn.md:73, :667-669;
             ssfecdsa.md:104-107; callers ssfecdsa.c:737 (k^-1), ssfec.c:662
             (SSFECPointToAffine z^-1, used for ECDSA R, ECDH S, KeyGen/PubKeyFromPrivKey Q),
             ssfrsa.c:893 (qInv in keygen)
  Problem:   ssfbn.md and ssfecdsa.md say SSFBNModInv is constant-time on the success path and
             that ECDSA signing is constant-time. The Fermat exponentiation is constant-time,
             but the function then checks a * r == 1 with SSFBNModMul, which is SSFBNMul plus
             SSFBNMod: a shift-and-subtract loop whose iteration count is
             BitLen(a*r) - BitLen(m) and whose add-back branch depends on each quotient bit.
             ssfbn.md itself lists SSFBNModMul and SSFBNMod as "do not use on secrets". Here
             a and r are the ECDSA nonce and its inverse.
  Failure:   P-256, SSFBNModInv(k) timed separately: the ModExp part is flat (49.46 us for
             full-length k and for k with its top 48 bits zero); the ModMul check takes
             4.10 us vs 3.32 us. Run time leaks the bit length of k * k^-1, which tracks
             leading zeros of the nonce: that is the Minerva / TPM-Fail class of leak, which
             lattice attacks turn into the private key from a few thousand signatures.
             The same check runs on Jacobian Z during PointToAffine (a projective-coordinate
             leak about the scalar, Naccache-Smart-Stern class) and on q / qInv in RSA keygen.
  Options:   (1) Do the check with SSFBNModMulCT (precondition a < m or r < m holds because
             r < m) — smallest change, keeps the non-prime-modulus rejection.
             (2) Drop the check for callers whose modulus is a known prime (curve p and n) and
             keep it for RSA. (3) Montgomery-form check through the already-built context.
             Recommend (1). A unit test can assert that SSFBNModInv no longer calls SSFBNMod
             (or compare iteration counts through a test hook) rather than timing.

BN-12  Low  OPEN  [code-read]
  Location:  ssfbn.c:925-957 (_SSFBNKaratsubaMul steps 5-7, tail loop)
  Problem:   ssfbn.md lists SSFBNMul as constant-time and the schoolbook paths say "No zero-limb

  Options:   (1) Run each propagation loop to its fixed bound with masked arithmetic (the same

BN-13  Low  OPEN  [code-read]
  Location:  ssfbn.c:265-335 (SSFBNToBytes), :382-430 (SSFBNToBytesLE)
  Problem:   Both exporters scan down from the top limb to the first non-zero limb and then
             count bytes, so run time reveals the number of leading zero limbs and bytes of the
             value. They are used to export secret values: the ECDH shared secret
             (ssfecdsa.c:940), the generated ECDSA private key (:594), RSA private key fields.
  Failure:   An ECDH shared x-coordinate with a leading zero limb exports measurably faster.
             Leading-zero leaks of DH secrets are the Raccoon-attack class; the signal here is
             one limb (2^-32 per output) or the byte count of the top limb.
  Options:   (1) When outSize >= a->len * 4 (the fixed-width export every caller here uses),
             skip the significance scan and write all limbs unconditionally; keep the scan only
             for the "does it fit" path. (2) Document.  Recommend (1).

  tracking, GenPrime top-bit forcing (BN-2), Miller-Rabin witness range.

ECDSA-5  Medium  FIXED (2026-11-19, opt-in; default off)  [code-read; fix verified red/green]
  Location:  ssfecdsa.c:671-779 (SSFECDSASign)
  Problem:   Sign has no fault countermeasure. RFC 6979 makes k a deterministic function of
             (d, hash), so two signatures of the same hash, one of them faulted (a glitch in
             the scalar multiplication, the inversion or s = k^-1 (e + r d)), give the attacker
             two equations in the same k and reveal d. This is the published differential fault
             attack on deterministic ECDSA (Poddebniak et al. 2018; Romailler and Pelissier
             2017). SSFEd25519Sign and both RSA sign paths in this tree already
             verify-after-sign for exactly this reason (ssfed25519.c:1460, ssfrsa.c:1084, :1300).
  Failure:   On an MCU an attacker who can glitch one signing call and request a second
             signature of the same message recovers the private key.
  Options:   (1) Verify-after-sign: derive Q = d*G (or take the caller's public key, as Ed25519
             does) and run the verify core on (r, s) before encoding; on failure wipe and
             return false. Costs roughly one verify per sign. (2) Hedged nonces (RFC 6979
             Sec. 3.6 extra randomness, as in draft-irtf-cfrg-det-sigs-with-noise) so the two
             signatures do not share k. (3) Both.  Recommend (1); (2) is also worth having
             where entropy is available.

  Also (see BN-10): ssfecdsa.md:104-107 says signing uses a constant-time inverse; that is
  false until BN-10 is fixed.

  Verified correct: RFC 6979 HMAC-DRBG steps a-h with the digest's HMAC (ECDSA-2), bits2int
  and bits2octets (ECDSA-3), retry on r or s == 0 via skip count (ECDSA-1), CT ModMulCT/ModAdd
  for r*d and k^-1 (e + r d), strict DER parse (length forms, minimal INTEGERs, no trailing
  data), r/s range checks, Jacobian r comparison including the r + n < p case, ECDH
  identity rejection and peer key validation, secret scrubbing in Sign/ECDH/KeyGen.

RSA-9  Low  OPEN  [code-read]
  Location:  ssfrsa.c:525, :534-535 (_SSFRSAPrivateOpCRT)
  Problem:   The private operation uses two routines ssfbn.md lists as variable-time on
             secret data: SSFBNModInvExt on the blinding factor r (extended Euclid, branch
             pattern depends on r) and SSFBNMod(&cp, &cB, p) / (&cq, &cB, q) with the secret
             primes as the modulus. Message blinding makes cB random, which limits the second;
             but a timing leak of r weakens the base blinding that is meant to cover c.
             Euclid-based inversion leaks are the "Big Numbers - Big Troubles" class (2020).
  Failure:   Timing of SSFRSASign* varies with r and with the quotient bits of cB / p.
             Exponent blinding (dp + eb*(p-1)) still protects the exponentiations.
  Options:   (1) rInv via CT exponentiation is not available (n is composite); instead blind
             the inversion: pick random b, compute (r*b)^-1 with ModInvExt, multiply by b
             (the standard BN_BLINDING approach), or derive r from rInv' as r = (rInv')^-1
             computed once. (2) Reduce cB mod p with ModMulCT(cB, 1) style CT reduction.
             (3) Document as accepted given blinding.  Recommend (3) now, (1)/(2) if RSA
             signing is used where timing is observable.
