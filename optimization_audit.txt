SSF OPTIMIZATION AUDIT: CODE SPACE, RAM AND PERFORMANCE
=======================================================
Audit date : 2026-11-24
Scope      : the production modules changed in the 48 hours to commit da0a07e (branch mqtt):
             ssftlsc, ssfx509, ssfbn, ssfmqttc, ssfmqttpkt, ssfnetsock, ssfcms, ssfpem,
             ssfpkey, ssfsm, ssfdtime, ssfiso8601 (with their headers and _opt files).
             Unit tests, tools and docs are out of scope; ssftls_certs.c was deleted.
Status     : audit only. Nothing here has been implemented; every item is OPEN.

HOW TO READ THIS FILE
---------------------
Labels      <MODULE>-<nn>, numbered within the module from largest potential to smallest.
            SAFE-<nn> are correctness / safety issues found during the audit (not savings);
            they come first.
            Labels are permanent: when an item is done or rejected, change its Status line
            rather than renumbering.
Categories  CODE (flash: text + rodata), STACK (a function's frame or a call chain's peak),
            STATIC (bss / data), STRUCT (a context or session struct the application
            allocates), HEAP, PERF (time or power).
Estimates   M = measured (a modified copy compiled with the flags below); E = estimated.
            V = also re-checked by the main session (independent rebuild or test run).
            Deltas are per item against the module baseline and are not always additive.
Status      OPEN | DONE <commit> | REJECTED <reason>.

Measurement
  Cortex-M4: arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Os -ffunction-sections
  -fdata-sections, SSF_TLS_CONFIG_ENABLE_TRACE=0, unit tests off,
  SSF_CONFIG_ENABLE_THREAD_SUPPORT=0. Stack from -fstack-usage. ssfnetsock uses POSIX
  sockets, so it is measured with host gcc -Os (x86-64; relative only).

  Note: the first measurement pass silently left unit tests on, because ssfassert.h and
  ssfoptions.h include ssfport.h by quoted include. That inflated ssftlsc (16,074 B),
  ssfbn (17,650 B) and ssfpem (739 B). The baselines below are the corrected ones (with
  ssfassert.h and ssfoptions.h shadowed too). Any future measurement must shadow all three.

  Prototypes: the auditors' modified copies are in the session scratch area
  (OPT/<group>/); a reboot may clear them. Each item is described fully enough here to
  redo without them.

SAFETY / CORRECTNESS ISSUES FOUND DURING THE AUDIT (not savings; fix independently)

SAFE-01  ssfnetsock: fd_set overflow for a descriptor >= FD_SETSIZE                [V]
  Location : _net/ssfnetsock.c:537 (lookup path), :907-908 (pollOpen)
  Issue    : FD_SET(fd, ...) on a stack fd_set with no FD_SETSIZE bound anywhere. On a
             glibc host a process with >= 1024 open descriptors writes past the fd_set
             (or aborts under _FORTIFY_SOURCE). Embedded stacks (lwIP) use small fds.
  Fix      : use poll() on POSIX (also NETSOCK-01), or check fd < FD_SETSIZE and fail.
  Status   : OPEN

SAFE-02  ssfbase64 (used by ssfpem / ssfpkey): data-dependent timing over key text    [V]
  Location : _codec/ssfbase64.c:46-57 (_SSFBase64GetEncoding), called per quad from
             _codec/ssfpem.c:166
  Issue    : each Base64 character is decoded by a linear search of the 65-character
             alphabet, so decode time depends on the character: a known side channel for
             PEM private keys. ssfbase64 was not changed in the window; it is listed
             because ssfpem / ssfpkey route private keys through it.
  Fix      : branch-free range decode (A-Z, a-z, 0-9, +, /, = by masks). Measured: +94 B
             code, 3.4x faster on the host (~150 -> ~40 cycles/char on M4, E); checked
             against the old table for all 256 byte values. Also PEM-01.
  Status   : OPEN

SAFE-03  ssfbn: a window size that does not divide 32 silently gives wrong results     [V]
  Location : _opt/ssfbn_opt.h:52-59 (SSF_BN_MODEXP_WIN_K), _crypto/ssfbn.c:2945
  Issue    : nWindows = bits / k truncates for k not dividing 32. The option's comment
             warns of this, but nothing enforces it: -DSSF_BN_MODEXP_WIN_K=3 builds an
             RSA / EC library that computes wrong answers (the BN unit test fails at
             ssfbn_ut.c:2561 with k=3, M).
  Fix      : nWindows = (bits + k - 1) / k (loop count still exponent-independent;
             SSFBNGetBit returns 0 past e->len), which also makes k=3 a valid stack choice
             (BN-03); or at least an #error for non-divisors.
  Status   : DONE (2026-11-25): the rounding fix, plus an #error outside k = 1 to 8. At the
             default k = 4 the count and the code are unchanged (ssfbn.o identical in size,
             same peaks). BN, RSA and ECDSA tests pass under ASan at every k from 1 to 8; HEAD
             at k = 3 fails (ssfbn_ut.c:2582). ModExp digest and RSA signatures identical at
             k = 2, 3, 4, 5. Test: ModExp against ModExpPub with exponents of 1 to 16 limbs
             (shorter than, equal to and longer than the modulus) and their top bits set,
             clear or a lone 1, so a k not dividing 32 has a partial top window; it fails on
             HEAD built at k = 3. Mutants (built at k = 3): 3 of 4 killed (round down, round
             short, the modulus length only); the 4th (one extra window) is equivalent, an
             all-zero window that squares Mont(1).

SAFE-04  ssfx509: SSF_X509_CONFIG_MAX_CHAIN_DEPTH cannot be overridden with -D
  Location : _opt/ssfx509_opt.h:21 (no #ifndef guard)
  Issue    : config hygiene, not a bug: the option cannot be set from the build line,
             unlike the other SSF options.
  Fix      : wrap it in #ifndef.
  Status   : OPEN

SAFE-05  ssfrsa: the 8 KB stack scrub does not reach the deepest freed frames      [V]
  Location : _crypto/ssfrsa.c:93 (_SSFRSAStackScrub, volatile uint8_t scratch[8192]);
             called at the end of SSFRSASignPKCS1, SSFRSASignPSS, SSFRSAKeyGen and
             _SSFRSAKeyGenDerive
  Issue    : ssfrsa.md promises that the scrub "overwrites the freed frames left by the
             underlying ssfbn primitives". It is a fixed 8,192 B, but the stack used below
             the scrubbing function is larger at every RSA cap (M4 -Os call graph, unit tests
             off; signing with the Euclid / shift-subtract paths it never takes excluded):
                 cap    keygen      sign (PKCS#1 and PSS)   sign after BN-01
                 4096   16,384 B    20,944 B                16,160 B
                 3072   12,416 B    15,888 B                12,256 B
                 2048    8,448 B    10,832 B                 8,352 B
             (keygen is 32 B deeper after BN-01: 16,416 / 12,448 / 8,480 B)
             Below the first 8 KB, freed ssfbn frames keep secret-derived words: Montgomery
             scratch of the CRT exponentiations, and in keygen the Miller-Rabin and inverse
             frames over p, q, lambda and d (extended Euclid does not wipe old_s / cur_s /
             tmp_s). Values the code zeroizes itself (CRT intermediates, the ModExp window
             table, the binary inverse's u / v / x1 / x2) are not affected. Defence in depth:
             it matters only where freed stack can be read later (a dump, a fault handler, a
             task reusing the stack). Frame positions are from the static call graph; inlining
             and call overhead move them by a few dozen bytes.
  Fix      : options, not yet chosen: (1) size the scrub per configuration from the measured
             depth below each caller (it does not raise the peak while it stays within the
             deepest path); (2) wipe in the ssfbn primitives that hold secret-derived scratch
             (MontMul / MontSquare / ConvertOut, Euclid), as the BN-11 scrub hook already
             does for the fast paths; (3) both. Each needs a timing and stack cost measurement.
  Found    : 2026-11-25, while measuring BN-05 (BN-05 brought Euclid's own frame, 9,344 ->
             5,248 B at 4096, inside the scrub; its callees still reach past it).
  Note     : (2026-11-25, BN-10) for option (2): SSFBNModInv now wipes its working value
             (p - 2 in keygen's qInv); BN-07 removed keygen's Euclid. Still unwiped in keygen:
             SSFBNModExp's Montgomery context (p and R^2 mod p, for qInv), and SSFBNGcd's two
             working values (p - 1 and q - 1 for lambda, and in the FIPS e-coprime check).
             SSFBNIsProbablePrime already wipes its five working values and its context, and
             SSFBNModExpHalf its context (BN-01); SSFBNMontInit no longer keeps a stack copy of
             R^2 (BN-09) nor SSFBNGenPrime of its candidates (BN-11). (Corrected the same day:
             this note first listed SSFBNIsProbablePrime as unwiped, from reading only part of
             the function, and missed SSFBNGcd.)
  Status   : OPEN

SAFE-06  ssfrsa: a private key with an even p or q asserts in signing                [V]
  Location : _crypto/ssfrsa.c:453-544 (_SSFRSAPrivKeyDecode); reached from SSFRSASignPKCS1 /
             SSFRSASignPSS -> _SSFRSAPrivateOpCRT -> SSFBNModExpHalf (SSFBNModExp before
             BN-01) -> SSFBNMontInit
  Issue    : the decoder checks that n is odd and that p, q are exactly half its width, but
             not that p and q are odd (SSFRSAPrivKeyIsValid does, but signing does not call
             it). SSFBNMontInit requires an odd modulus (SSF_REQUIRE), so a malformed key DER
             with an even prime stops in an assertion instead of the sign call returning
             false. Reproduced on HEAD 1ba831b (before BN-01) with an
             OpenSSL RSA-2048 key whose p had its low bit cleared: "SSF Assertion:
             _crypto/ssfbn.c:2506". BN-01 does not change it.
  Fix      : reject an even p or q in _SSFRSAPrivKeyDecode, next to the even-n check, plus
             a unit test per sign function; IsValid's own check then becomes redundant.
  Found    : 2026-11-25, BN-01 correctness and security audit.
  Status   : OPEN

BN-01  STACK  SSFBNModExpMont 10,440 -> 4,792 B at RSA-4096 (sign chain 12,624 ->
       ~6,976 B) with an option to size it for the half-width moduli in use              M
  Location : _crypto/ssfbn.c:2864, 2888-2891
  What     : the table and working values are sized for a full-width modulus, but every
             in-tree secret ModExp uses a half-width one (RSA CRT p and q; ModInv qInv mod
             p; IsProbablePrime on half-size candidates). This frame is on the TLS
             client's RSA client-certificate signing path (ssftlsc.c:2210).
  Change   : option SSF_BN_MODEXP_MAX_LIMBS (default SSF_BN_MAX_MOD_LIMBS) for
             ModExpMont, ModExp and ModInv; RSA builds set SSF_RSA_MAX_HALF_LIMBS.
             ModExp's own mont drops ~540 B more if sized the same way (E).
  Risk     : medium; constant-time unchanged; full-width SSFBNModExp unit tests need the
             default or gating. Combines with BN-03 / BN-04.
  Re-measured (2026-11-25, M4 call graph, RSA caps 4096 / 3072 / 2048): the figures above
             are the ModExp branch, not the signing peak. The sign peak runs through the
             blinding inverse (_SSFRSAPrivateOpCRT -> SSFBNModInvExt -> _SSFBNModInvExtEuclid,
             28,904 B at 4096) above the ModExp branch (26,784 B), so BN-01 alone saves 0 B on
             the RSA sign and TLS client pollOpen peaks at every cap. It pays only after BN-05
             / BN-07 lower the inverse branch (E at 4096: BN-05 alone 28.9 -> 26.8 KB; BN-05 +
             BN-01 24.8 KB).
             The change as written narrows the public SSFBNModExp / ModExpMont to half width
             in RSA builds (a full-width modulus would fail SSF_REQUIRE), against the
             SSF_BN_MAX_MOD_LIMBS design in ssfbn.md: keygen 27,120 -> 25,496 B, -4 B code.
             Preferred non-narrowing design (prototyped): public functions unchanged over a
             shared constant-time core taking caller storage; new SSFBNModExpHalf (the
             SSFBNModInvSmall precedent) used only by the RSA CRT, with a compile-time check
             that the CRT primes fit. ModExp branch 26,784 -> 22,016 B (4096), 20,384 ->
             16,768 (3072), 13,984 -> 11,512 (2048); keygen +32 B; code +236 B; host time
             unchanged within noise, results bit-identical to HEAD; BN / RSA / ECDSA unit
             tests pass.
  Status   : DONE (2026-11-25): the non-narrowing design, plus SSFBNModExpHalf wiping its
             context (it holds the prime). SSFBNModExp / ModExpMont keep their signatures,
             contracts and full-width storage over a shared constant-time core
             (_SSFBNModExpMontCore, caller storage of TBL_N + 4 residues); SSFBNModExpHalf
             takes moduli up to SSF_BN_HALF_MOD_LIMBS; the RSA CRT calls it, with a
             compile-time check that SSF_RSA_MAX_HALF_LIMBS fits. Measured (M4 -Os, unit
             tests off; on gives the same deltas): RSA sign stack actually used (PSS) 26,768
             -> 21,984 B at 4096, 20,368 -> 16,736 at 3072, 13,968 -> 11,488 at 2048 (PKCS#1
             the same deltas); static sign peak 26,768 -> 24,752 / 20,368 -> 18,856 / 13,968
             -> 12,968 (Euclid's branch, never run when signing, is now the deepest); TLS
             client pollOpen with an RSA key 27,496 -> 25,480 at 4096; keygen +32 B (the core's
             call frame under the public ModExpMont; BN-04 would remove it); code +244 B at
             every cap. Host: RSA-2048 / 4096 signing time unchanged
             within noise, signatures byte-identical to HEAD and verified by OpenSSL.
             Tests (red first: the API did not exist): ModExpHalf equals ModExp at every
             width 1..SSF_BN_HALF_MOD_LIMBS with exponents of 1, n and n + 3 limbs; base 0 / 1,
             exponent 0, m = 1; the four wipe reports, all zero; the precondition one limb
             wider. BN / RSA / ECDSA unit tests pass, ASan / UBSan clean; X.509, CMS and TLS
             client tests pass against it. Mutants (ASan): full-width cap on half storage,
             each wipe, exponent length ignored, short table stride and swapped CRT primes are
             killed; `one` sharing `picked`'s slot (equivalent, see BN-04), the redundant
             width precondition (MontInit's cap check still fires) and the CRT calling
             ModExp again (same result; only the stack differs) survive. Audit: untrusted
             keys cannot reach the new precondition (the decoder fixes p, q at exactly half
             n's width, bounded by SSF_RSA_MAX_KEY_BYTES); found SAFE-06 (pre-existing).
             Docs: ssfbn.md, ssfrsa.md, README footnotes 38 / 48, ssftlsc.h.

BN-02  STACK / CODE / PERF  SSFBNModExpMontPub frame 3,128 -> 1,072 B; RSA verify chain
       5,344 -> 3,256 B (-2,088 with BN-06); -39 B code; e=65537 10% faster (host)       M V
