ssfjson
----------------------------------------------------------------------------------------------

JSON-1  High  OPEN  CODE  [measured, ASan global-buffer-overflow]
  Location:  ssfjson.c:191 (_SSFJsonArray element loop), read at ssfjson.c:190
  Problem:   While scanning an array for the requested element, _SSFJsonArray passes the
             caller's path to every element, not only the selected one. A sibling element that
             is itself an array then reads path[depth] as a size_t index (memcpy of 8 bytes),
             even when that path entry is an object key string for the selected element.
             _SSFJsonNameValue already avoids this for objects by passing a NULL path to
             members that do not match; arrays do not. The reverse case (a sibling object
             running strlen / strncmp on a path entry that is a size_t pointer) follows from
             the same loop [code-read].
  Failure:   ssfjson_ut.c:865, SSFJsonGetType(_jtsComplex[i], path) with path[2] = "hex1":
             8-byte read from a 5-byte string literal. Any caller whose path goes through an
             array that has array or object siblings is exposed; the caller's path is valid.
  Options:   (1) In the array loop, pass path only for the element whose index matches
             (NULL otherwise), as _SSFJsonNameValue does (recommended). (2) Also check the
             path entry's kind, which the API cannot express (path entries are untyped).

JSON-2  High  OPEN  CODE  [suspected, code-read only]
  Location:  ssfjson.c:267 (_SSFJsonNameValue non-matching branch), ssfjson.c:186 / 281
  Problem:   A non-matching member is parsed with _SSFJsonValue(..., NULL, 0, ...): depth is
             reset to 0, so the SSF_JSON_CONFIG_MAX_IN_DEPTH check in _SSFJsonObject /
             _SSFJsonArray restarts below every skipped key. Recursion depth on a path miss
             may then be bounded only by SSF_JSON_CONFIG_MAX_IN_LEN, not by the depth limit.
  Failure:   (to confirm) hostile input such as {"a":{"a":{"a":...}}} nested far past the
             depth limit, looked up with a path that does not match, recursing until the
             stack overflows on an MCU.
  Options:   Confirm first with a nesting test and stack measurement. If real: pass depth
             (not 0) on the non-matching branch so the limit counts every level.

JSON-3  Low  OPEN  TEST  [measured, compile error]
  Location:  ssfjson_ut.c:1409
  Problem:   The JSON unit test calls SSFGObjIsMemoryBalanced(), which ssfgobj.h declares only
             when SSF_CONFIG_GOBJ_UNIT_TEST == 1. With the JSON test on and the GObj test off
             the runner does not compile.
  Options:   Guard the call with SSF_CONFIG_GOBJ_UNIT_TEST, or declare the helper whenever
             any unit test that uses it is enabled.

HEX-1  Low  OPEN  TEST  [measured, ASan global-buffer-overflow]
  Location:  ssfhex_ut.c:105; ssfhex.c:101 (reverse branch)
  Problem:   The test calls SSFHexBytesToBin("1234", strlen("1234") + 200, ...). ssfhex.md
             requires inLenLim <= strlen(in). In forward order the decoder stops at the NUL and
             returns false; in reverse order it starts at in[inLenLim - 2], 200 bytes past the
             string.
  Options:   (1) Fix the test to stay within the contract (recommended). (2) Optionally harden
             the decoder: the parameter name "Lim" invites passing a buffer size, so stopping
             at a NUL (or bounding with strnlen first) would make the reverse path safe too.

B64-1  Low  OPEN  TEST  [measured, ASan global-buffer-overflow]
  Location:  ssfbase64_ut.c:127 (block-vector loop); ssfbase64.c:69
  Problem:   The test runs the internal 4-character block decoder SSFBase64Dec32To24 over
             every _b64BlockUT vector, including { "", 0, "" }. The block decoder always reads
             four characters; its only library caller, SSFBase64Decode, always supplies four.
  Options:   Skip the empty vector in the block loop and keep it in the SSFBase64Decode tests
             (recommended).

UBJSON-1  Low  OPEN  CODE  [measured, UBSan]
  Location:  ssfubjson.c:1123 (UBJ_TYPE_INT64 encode); htonll in ssfport.h:295
  Problem:   htonll is applied to the signed int64_t value; the macro's left shifts of a
             negative or large signed value are undefined behaviour ("left shift of 255 by 56
             places cannot be represented in type 'long int'"). Works on gcc today; a compiler
             may miscompile it.
  Options:   Convert to uint64_t before htonll (and back) in ssfubjson (recommended), and/or
             cast inside the htonll / ntohll macros.

----------------------------------------------------------------------------------------------

DEC-1  Low  OPEN  CODE  [measured, UBSan]
  Location:  ssfdec.c:332
  Problem:   Parsing INT64_MIN ("-9223372036854775808"): u64 = 2^63, (int64_t)u64 is
             implementation-defined and its negation overflows (UB). The value comes out right
             on two's-complement gcc.
  Options:   Compute the negative result without signed overflow, e.g.
             *val = (int64_t)(0u - u64) on the u64 == 2^63 path, or -(int64_t)(u64 - 1) - 1.
