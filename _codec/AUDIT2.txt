MATCH-4  Low  DOC (2026-11-19)  [code-read]
  Location:  ssfmatch.c:187-264 (SSFMatchPath); ssfmatch.md:51-53
  Problem:   A {param} binds any non-empty path segment byte for byte, including "." and "..",
             and percent-encoded forms such as "%2e%2e" or "%2F" are not decoded. ssfmatch.md
             says no percent-decoding or normalization is applied, but does not spell out the
             consequence: a router pattern such as "/files/{name}" hands ".." to the handler,
             and a handler that joins it onto a filesystem path or object key walks out of
             the intended directory (the classic path-traversal bug in REST routers).
  Failure:   SSFMatchPath("/files/{name}", "/files/..", ...) returns true with name = "..".
  Options:   (1) Document it: parameter values are raw segments that may be ".", ".." or
             percent-encoded and must be validated before use as paths or keys (recommended).
             (2) Reject "." and ".." values in SSFMatchPath (behaviour change; does not cover
             encoded forms).

  Verified correct: StrI / StrNI stop at the first terminator and never read past it; the glob
  wildcard-run cap bounds recursion depth (MATCH-2's cost remains, see above); SSFMatchPath
  bounds every write by paramsOutOptSize, reports the true placeholder count, zeroes the count
  on every false return, and treats '?' / '#' as the end of the path only after the pattern is
  exhausted.

  Third pass, ssfmatch only (2026-11-19), after the MATCH-2 rewrite (uncommitted at the time):
  every line of ssfmatch.c / .h / .md and _opt/ssfmatch_opt.h re-read; a 3,000,000-iteration
  random fuzz of all five functions under ASan + UBSan (glob cross-checked against a recursive
  reference with bytes 0x80 / 0xFF in pattern and subject, SSFMatchPath checked for non-empty
  values free of '/', '?', '#' and a zero count on every false return): no sanitizer report,
  no mismatch. Probes in scratchpad only.

MATCH-5  Low  FIXED (2026-11-19)  [demonstrated; fix verified red/green]
  Location:  ssfmatch.c SSFMatchPath, placeholder-name scan
             (while ((*nameEnd != '}') && (*nameEnd != '\0')) nameEnd++;)
  Problem:   A placeholder name runs to the next '}' and may contain any byte, including '/',
             '{', '?', '#' and space. A mistyped pattern is therefore not rejected as malformed
             but silently changes the route's shape: "/a/{id/{x}" is one placeholder named
             "id/{x" and "/a/{id/b}" one named "id/b", so both match the one-segment path
             "/a/7" instead of failing. Patterns are developer-supplied, so this is a
             robustness issue, not an attacker-reachable one.
  Failure:   SSFMatchPath("/a/{id/{x}", "/a/7", p, 4, &n) -> true, n = 1, name = "id/{x".
  Options:   (1) Treat a name containing '/', '{', '?' or '#' as a malformed pattern and return
             false, as an unterminated '{' or an empty '{}' already does (recommended).
             (2) Restrict names to [A-Za-z0-9_] (RFC 6570 varchar without pct-encoding).
             (3) Document.

MATCH-6  Low  DOC (2026-11-19)  [demonstrated]
  Location:  ssfmatch.md Notes (glob); ssfmatch.c _SSFMatchGlobInternal
  Problem:   Glob applies no path semantics: '*' crosses '/' and matches "..", and nothing is
             normalized. ssfmatch.md warns that '*' crosses '.' for hostnames (MATCH-3) and that
             SSFMatchPath values may be ".." (MATCH-4), but not that a glob used as a path
             access-control check is bypassable: "/public/*" accepts "/public/../admin", and
             "/admin/*" is evaded by "//admin/x" or "/./admin/x".
  Failure:   SSFMatchGlob("/public/*", "/public/../admin") -> true.
  Options:   (1) Document: glob is plain string matching; normalize (and percent-decode) a path
             before using a glob on it for access control (recommended). (2) None in code: a
             path-aware glob would be a different function.

MATCH-7  Low  DOC (2026-11-19)  [demonstrated]
  Location:  ssfmatch.md SSFMatchGlob description and Notes ("'?' (exactly one character)")
  Problem:   '?' matches exactly one byte, not one character, and '*' can end inside a
             multi-byte UTF-8 sequence. For UTF-8 subjects "?" does not match "\xC3\xA9" (e
             acute) but "??" does. The case-folding note already says folding is ASCII-only;
             the byte unit is not stated.
  Failure:   SSFMatchGlob("?", "\xC3\xA9") -> false; SSFMatchGlob("??", "\xC3\xA9") -> true.
  Options:   (1) Document that patterns and subjects are byte strings and '?' matches one
             byte (recommended). (2) UTF-8-aware '?' (more code, and the API is byte-oriented
             everywhere else).

ASN1-14  Medium  FIXED (2026-11-19)  [measured; fix verified red/green]
  Location:  ssfasn1.c:635-708 (SSFASN1DecGetTime), :698 (year range check);
             _time/ssfdtime.h:64 (SSFDTIME_EPOCH_YEAR_MAX 2199); ssfx509.c:912-913;
             ssfx509.md:89-91
  Problem:   SSFASN1DecGetTime returns false for any year after 2199, because the value is
             converted through ssfdtime, whose range ends at 2199-12-31. RFC 5280 4.1.2.5
             specifies GeneralizedTime 99991231235959Z as the notAfter of a certificate with
             no well-defined expiration date, and conforming verifiers must accept it.
             ssfx509.md:89-91 even says the value "is treated as an ordinary far-future
             date". In fact SSFX509Parse fails, so the certificate can be neither parsed nor
             used in a chain.
  Failure:   GeneralizedTime 99991231235959Z: DecGetTime = 0. An OpenSSL 3.5 self-signed
             P-256 certificate with -not_after 99991231235959Z: SSFX509Parse = 0 and
             SSFX509VerifyChainPurpose = 0; the same certificate with a 1-year validity
             parses. IEEE 802.1AR device identity (IDevID) certificates, common on the
             embedded devices SSF targets, use exactly this notAfter, so a device could not
             verify its own or its peers' manufacturer certificates.
  Reach:     Any certificate (leaf, intermediate or trust anchor) or CMS signer certificate
             with a notAfter (or notBefore) after 2199. Fails closed, so it is a correctness /
             availability defect, not a bypass.
  Options:   (1) In DecGetTime, after full syntax and calendar validation, map a time after
             2199-12-31T23:59:59Z to a saturating value (UINT64_MAX, or
             SSFDTIME_UNIX_EPOCH_SEC_MAX + 1) instead of failing; document it. notAfter
             comparisons in SSFX509IsValid then work unchanged (recommended).
             (2) Special-case only the exact RFC 5280 value 99991231235959Z.
             (3) Widen ssfdtime's range (larger change to another module).
             Calendar validation for years 2200-9999 needs its own leap-year check, since
             ssfdtime cannot be used there.

  Verified correct: tag / length parsing (definite, minimal long form, high-tag 31..127, tag 0
  rejected), every Get* bounded by the TLV length and advancing only on success (ASN1-7),
  BOOLEAN / INTEGER / unsigned / BIT STRING (unused bits and padding) / NULL / OID (canonical
  sub-identifiers, 32-bit cap) / string-type body checks, UTCTime pivot at 50, encoders' size
  guards, minimal INTEGER and BIT STRING rules, in-place EncWrap (ASN1-12).

X509-17  Low  FIXED (2026-11-19)  [measured; fix verified red/green]
  Location:  ssfx509.c:2435-2465 (_SSFX509ParseIPv4), used by _SSFX509IPAddressMatch and the
             server-auth hostname check in SSFX509VerifyChainPurpose
  Problem:   The IPv4 reference-identity parser accepts leading zeros and reads every octet as
             decimal, so "010.0.0.1" is taken as 10.0.0.1. The standard resolver functions
             (inet_aton, and getaddrinfo on many C libraries) read a leading 0 as octal and
             connect "010.0.0.1" to 8.0.0.1. When an application passes the same user-supplied
             host string to both, it connects to one address and verifies the certificate
             against another. This is the leading-zero IP ambiguity behind CVE-2021-29921 and
             similar bugs.
  Failure:   SSFX509MatchIPAddress("010.0.0.1", 10.0.0.1) = 1 and against 8.0.0.1 = 0, while
             inet_aton("010.0.0.1") = 8.0.0.1.
  Options:   (1) Reject a multi-digit octet with a leading zero, so such a string is neither an
             IPv4 literal nor (with its dots and digits) a plausible DNS match (recommended).
             (2) Document that callers must pass a canonical dotted-decimal address.

X509-18  Low  FIXED (2026-11-19)  [code-read; fix verified red/green]
  Location:  ssfx509.c:806-822 (Name Constraints parse stores every iPAddress subtree),
             :3012-3026 (_SSFX509NCIPMatch IPv4 only), :3052-3100 (_SSFX509NCValidateCert)
  Problem:   iPAddress subtrees are stored as enforced whatever their length, but the matcher
             only handles 8-byte IPv4 address+mask. An IPv6 subtree (32 bytes), or a malformed
             one of any other length, never matches. For permitted subtrees that fails closed
             (an IPv6 SAN then has no matching permitted subtree and is rejected). For excluded
             subtrees it fails open: an IPv6 SAN inside an excluded IPv6 range passes the Name
             Constraints check. This is the same fail-open shape as X509-16.
  Reach:     A name-constrained CA issuing an IPv6 SAN. Low impact today: SSF's hostname check
             supports only IPv4 literals, so an IPv6 SAN can never be used to authenticate a
             TLS server here.
  Options:   (1) Record an iPAddress subtree that is not 8 bytes as an unenforced form, so any
             subordinate with an iPAddress SAN is rejected as for other unenforced forms
             (recommended). (2) Implement 32-byte IPv6 address+mask matching.

X509-20  Low  FIXED (2026-11-19)  [code-read; fix verified red/green]
