JSON-1  High  FIXED (2026-11-19)  CODE  [measured, ASan; fix verified red/green]
  Location:  ssfjson.c:191 (_SSFJsonArray element loop), read at ssfjson.c:190
  Problem:   While scanning an array for the requested element, _SSFJsonArray passes the
             caller's path to every element, not only the selected one. A sibling element that
             is itself an array then reads path[depth] as a size_t index (memcpy of 8 bytes),
             even when that path entry is an object key string for the selected element.
             _SSFJsonNameValue already avoids this for objects by passing a NULL path to
             members that do not match; arrays do not. The reverse case (a sibling object
             running strlen / strncmp on a path entry that is a size_t pointer) follows from
             the same loop [code-read].
  Failure:   ssfjson_ut.c:865, SSFJsonGetType(_jtsComplex[i], path) with path[2] = "hex1":
             8-byte read from a 5-byte string literal. Any caller whose path goes through an
             array that has array or object siblings is exposed; the caller's path is valid.
  Options:   (1) In the array loop, pass path only for the element whose index matches
             (NULL otherwise, depth unchanged), as _SSFJsonNameValue does (chosen). (2) Also
             check the path entry's kind, which the API cannot express (untyped entries).

JSON-2  High  FIXED (2026-11-19)  CODE  [measured; fix verified red/green]
  Location:  ssfjson.c:267 (_SSFJsonNameValue non-matching branch), ssfjson.c:186 / 281
  Problem:   A non-matching member was parsed with _SSFJsonValue(..., NULL, 0, ...): depth
             reset to 0, so the SSF_JSON_CONFIG_MAX_IN_DEPTH check in _SSFJsonObject /
             _SSFJsonArray restarted below every skipped key. SSFJsonIsValid passes an
             all-NULL path, so every member is "skipped": object nesting had no depth limit
             in validation or in any lookup; only SSF_JSON_CONFIG_MAX_IN_LEN bounded it.
             Arrays were limited (their elements keep the depth).
  Failure:   SSFJsonIsValid accepted {"a":{"a":...}} nested 5, 6, 7, 8 and 340 levels (the
             most that fits in 2047 bytes) with a limit of 4; SSFJsonGetType walked all 340.
             Each object level is _SSFJsonObject + _SSFJsonNameValue + _SSFJsonValue frames:
             48 + 72 + 56 = 176 B on Cortex-M4 (184 B on M0+), so one 2 KB input recursed
             through about 60 KB of stack. SSFJsonGObjCreate validates with SSFJsonIsValid
             first, so it was exposed too (its own parser rejects deep input, but only after
             that validation pass).
  Options:   (1) Pass depth (not 0) on the non-matching branch (chosen). (2) A separate
             never-reset recursion counter (rejected: the existing limit already means this).

JSON-4  Low  OPEN  CODE  [measured]

  Problem:   SSFJsonGObjCreate's own parser counts depth one level earlier than the

JSON-5  High  FIXED (2026-11-20, with JSON-7)  CODE  [measured; fix verified red/green]
  Location:  ssfjson.c:212-240 (_SSFJsonValue scalar cases), reached from _SSFJsonNameValue and
             _SSFJsonArray on a path match
  Problem:   A path that continues past a scalar still matches. When a key or index on the path
             matches and its value is a string, number, true, false or null, _SSFJsonValue
             reports that value's type and span without checking that the path ends there.
  Failure:   SSFJsonGetType("{\"a\":\"s\"}", a.b) and SSFJsonGetType("[\"s\"]", [0].x) return
             SSF_JSON_TYPE_STRING instead of SSF_JSON_TYPE_ERROR (path not found), so
             SSFJsonGetString on a.b returns "s". A device expecting {"a":{"b":...}} accepts a
             document of a different shape and reads the wrong field without noticing.
  Options:   Report a scalar as the match only when the path ends at it (path[depth + 1] ==
             NULL), otherwise treat the lookup as not found (recommended). Add tests for
             objects, arrays and every scalar type.

JSON-6  High  FIXED (2026-11-20)  CODE  [measured; fix verified red/green]  (found in the
                    JSON-1 change audit; pre-existing)
  Location:  ssfjson.c:192-196 (_SSFJsonArray: djt / valStart / valEnd copied for the selected
             element)
  Problem:   When the element at the path index does not contain the rest of the path, nothing
             sets djt, valStart or valEnd, and the loop copies them into *jt / *start / *end
             anyway: an indeterminate value (undefined behaviour) becomes the result.
  Failure:   SSFJsonGetType("[{\"b\":1}]", [0].zz) returns 32764, 21887, 21849 or 21910 (gcc
             -O0 / -O1 / -O2 / -Os) or -16843010 with pattern-initialised locals, not
             SSF_JSON_TYPE_ERROR (0); same at HEAD before JSON-1. A caller switching on the
             type gets a value outside the enum. If the stale value equals a real type, the
             getters would use the stale start / end as offsets into js [code-read; not
             observed, the stale values seen were never a valid type].
  Options:   (1) Pass the caller's start / end / jt straight to the element at the path index,
             as matched object members already do, and keep the locals for the other elements
             only (chosen). (2) Set djt = SSF_JSON_TYPE_ERROR before each element and copy
             start / end only with a real type.

JSON-7  High  FIXED (2026-11-20)  CODE  [measured; fix verified red/green]  (found in the
                    JSON-1 change audit; pre-existing)
  Location:  ssfjson.c:190 (memcpy of path[depth] as a size_t index), ssfjson.c:262-264 (key
             compare of path[depth] as a string)
  Problem:   Path entries are untyped: an array reads its entry as a size_t index, an object
             as a key string. The caller cannot choose which one applies, the document's shape
             does. JSON-1's fix stops unselected elements from using the path, but a document
             whose shape differs from the caller's path still makes the selected element read
             a key as an index (or an index as a key).
  Failure:   (1) SSFJsonGetInt("{\"a\":[1,2]}", a.hex) with "hex" in a 4-byte buffer: ASan
             stack-buffer-overflow, 8-byte read. (2) Key "a" followed by zero bytes reads as
             index 97: SSFJsonGetInt on {"cfg":[1000,...,1099]} with path cfg.a returns true and
             1097, an array element returned for a member lookup. Same at HEAD.
  Options:   Needs an API decision: the parser must know each entry's kind. (1) Typed path
             entries (SSFJsonPath_t: kind + key or index pointer) (chosen; also fixes JSON-5).
             (2) A parallel kind bitmask / array (a wrong bit brings the over-read back).
             (3) A tagged index entry (old callers break silently at run time). (4) Checks
             only (impossible with untyped pointers).

JSON-8  High  FIXED (2026-11-20)  CODE  [measured, ASan global-buffer-overflow; fix verified
                    red/green]  (found in the JSON-6 change audit; pre-existing)
  Location:  ssfjson.c:264-268 (_SSFJsonNameValue match branch), ssfjson.c:304 (_SSFJsonObject
             records *start on entry), ssfjson.c:406-412 (SSFJsonGetString span); ssfjson.md
             (Limitations)
  Problem:   ssfjson.md says the parser "matches only the first occurrence" of a duplicate key,
             but every member whose key matches is parsed with the caller's results. Each
             later duplicate writes them again, so the last occurrence wins; and a later
             duplicate that does not complete the path still writes *start (every nested
             object records its start on entry) while the type and end stay from the earlier
             match. The getters trust that span.
  Failure:   (1) {"a":"1","a":"2"} with path a, and [{"a":"1","a":"2"}] with [0].a, return "2".
             (2) {"a":{"b":"x"},"a":{"c":2}} with path a.b: type STRING, start 19 (the second
             object), end 12 (the first string). SSFJsonGetString computes len = end - start
             + 1, which wraps to a huge size_t, and reads past the end of the document (ASan
             global-buffer-overflow at ssfjson.c:416) until the output buffer is full,
             copying bytes from beyond the document into out. The document alone triggers it;
             the caller's path is valid. (3) {"a":{"b":"x"},"a":"y"} with a.b returns "y" (with
             JSON-5). Same spans at fb11856, before the JSON-1 / 2 / 6 fixes. Duplicate keys
             are also a known source of parser differentials: a validator that reads the first
             value and a device that reads the last can disagree about one document.
  Options:   (1) Match only the first occurrence, as documented: once a member has matched,
             parse later duplicates without the path, so only one match ever writes the
             results. (2) Reject documents with duplicate keys (stricter; RFC 8259 leaves
             their meaning undefined). (3) In addition to either, reject a span with
             end < start before any getter uses it (cheap defence in depth). Chosen: 1 + 3.
  Follow-up: First-occurrence matches ssfjson.md, but JavaScript's JSON.parse and Python's
             json take the LAST occurrence, so a peer using them and a device using ssfjson
             can still read different values from a document with duplicate keys. Options:
             (1) keep first occurrence and document the risk, (2) reject duplicates, (3) a
             config option. DECIDED (2026-11-20, Jim): option 1; ssfjson.md now warns that
             other parsers use the last occurrence and that a document crossing another
             parser should have duplicates rejected or normalised there.
