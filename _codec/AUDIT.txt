SSF _codec CORRECTNESS AND SECURITY AUDIT
=========================================

Date:        2026-11-18
Branch:      x509 (HEAD 6768015)
Scope:       ssfasn1, ssfx509, ssfmatch, ssfstr (the _codec modules _crypto depends on:
             ssfasn1 directly from ssfcms / ssfrsa / ssfecdsa, ssfx509 from ssfcms, ssfmatch
             and ssfstr through ssfx509). Implementation .c/.h and their .md contracts; the
             _ut.c files were used for intent and coverage. Style, naming and comment issues
             were out of scope.
Method:      Audited sequentially, one module at a time, each reviewer given the earlier
             modules' findings so cross-module issues are reported once at their root cause and
             cross-referenced (e.g. X509-6 "root cause ASN1-7"). Every line of each .c was read.
             Linux x86-64 gcc harnesses with -fsanitize=address,undefined demonstrated findings
             (marked [demonstrated]); fuzzing: 3,000,000 mutated inputs through every ssfasn1
             decoder and 5,000,000 mutated certificates through SSFX509Parse and the matchers
             found no out-of-bounds access or UB (the X509-1 hang was patched out of the fuzz
             build). Certificates for chain tests were made with the openssl CLI and checked
             against openssl verify. The lead reviewer re-read the source for every High
             finding and for ASN1-7 / X509-6 and STR-2 (marked [verified 2026-11-18]).
             Repository files were not modified by the audit.

Severity scale
  Critical  wrong results, memory corruption or security break in normal use
  High      wrong result on reachable edge cases, undefined behaviour, process halt on
            hostile input where the contract says "returns false"
  Medium    contract/doc mismatch, missing DBC that permits corruption, portability break,
            weakened security margin
  Low       minor correctness nit, latent UB, doc drift

Status values: OPEN, FIXED (date), WONTFIX (reason), DOC (fixed by documentation change)
               The commit for a FIXED item is found with: git log --oneline --grep=<label>

  Memory safety: no out-of-bounds access or UB was found on any hostile-input path (certificate

  The serious findings are availability (X509-1 hang, X509-2 trap) and RFC 5280 / DER
  strictness gaps that fail open (X509-3, X509-6, X509-8 and their ASN1 root causes).

Suggested fix order
  1. X509-1        check SSFASN1DecSkip's return in the uniqueID skip loop (one-line fix; any
                   certificate from the network can hang the device today).
  2. X509-2        reject an empty / malformed RSA (and ECDSA) key in ssfx509 before calling
                   verify, so a hostile intermediate returns false instead of trapping.
  3. X509-3        Name Constraints fail closed: reject when excluded subtrees exceed the cap
                   or the body is malformed.
  4. ASN1-7 + X509-6, ASN1-1 + X509-8
                   don't advance *next on failure / check the critical BOOLEAN's return; reject
                   negative and non-minimal INTEGERs in DecGetIntU64 and fail closed on pathLen.
  5. ASN1-2..6     DER strictness (minimal lengths, INTEGER, BOOLEAN, BIT STRING, EncInt).
  6. X509-4, -5, -7  remaining Medium path-validation gaps; then STR-1..5 (unused APIs, but
                   public), then Low items at discretion.

ssfasn1
----------------------------------------------------------------------------------------------

Branch x509, HEAD 6768015. Scope: _codec/ssfasn1.c (1108 lines), ssfasn1.h, ssfasn1.md; the
_ut.c and the callers in ssfx509.c, ssfcms.c, ssfrsa.c and ssfecdsa.c were read to learn
intended use and reach. Every line of ssfasn1.c was read. That covers the TL parser
(_SSFASN1ParseTL), every typed decoder, the time decoders and how they hand off to ssfdtime
(SSFDTimeStructInit range checks return false, never trap), and every encoder's measure and
write paths. Memory safety is solid: no out-of-bounds read or write, no arithmetic overflow and
no data-reachable SSF_REQUIRE was found. All length arithmetic is uint32_t, guarded as
"contentLen > bufLen - headerLen". A random mutation fuzzer ran 3,000,000 inputs through every
decoder with recursive descent into constructed elements, built with
-fsanitize=address,undefined: zero findings. The weaknesses are in DER strictness. The decoder
is much more lenient than the .md says (lengths, INTEGER, BOOLEAN, BIT STRING, cursor behaviour
on failure). Separately, the .md says SSFASN1EncInt makes INTEGERs canonical, and it does not.
Harness: asn1/h.c (behaviour probes), asn1/fz.c (fuzzer); output in asn1/h.out. Both are in the
scratch dir. Build: gcc -fsanitize=address,undefined with _codec/ssfasn1.c, _time/ssfdtime.c
and _edc/ssffcsum.c.

ASN1-1  High  FIXED (2026-11-18)  [demonstrated] [verified 2026-11-18]
  Location:  ssfasn1.c:227-252 (SSFASN1DecGetIntU64)
  Problem:   The sign bit is never checked. The bytes are treated as an unsigned magnitude, so
             a negative INTEGER decodes to a large positive value. The .md promises false for
             a negative INTEGER. An empty INTEGER (02 00) decodes as 0, and non-minimal forms
             (02 03 00 00 01) decode as 1. The .md says such INTEGERs are rejected.
  Failure:   02 01 FF (-1) -> true, 255.  02 01 80 (-128) -> true, 128.  02 00 -> true, 0.
             In ssfx509 (ssfx509.c:369-372), a basicConstraints pathLenConstraint of -1, which
             is invalid, becomes 255 and is clamped to 127. A malformed CA constraint therefore
             becomes "nearly unlimited" when it should fail the parse. A negative PSS
             saltLength (ssfx509.c:220) reads as 255.
  Reach:     Certificate and CMS bytes reach this through ssfx509 (version, pathLen, PSS
             saltLength), ssfcms (versions at ssfcms.c:348/497) and ssfrsa (private key
             version, ssfrsa.c:385). The current callers reject most out-of-range results.
             pathLen is the case where the wrong value is accepted.
  Evidence:  242   if (intLen > 1u && intBuf[0] == 0x00u) start = 1;
             244   if ((intLen - start) > 8u) return false; /* Too large for uint64_t */
             md:397 "Returns `false` if the INTEGER is negative or its unsigned value would
                    exceed `UINT64_MAX`."
             harness: "B IntU64 02 01 FF (-1) -> ret=1 val=255"
                      "B IntU64 02 01 80 (-128) -> ret=1 val=128"
                      "C IntU64 02 00 (empty) -> ret=1 val=0"
                      "C IntU64 02 03 00 00 01 (non-minimal) -> ret=1 val=1"
  Options:   (1) Reject intLen == 0, reject (intBuf[0] & 0x80) != 0, and reject a leading 00
             when the next byte is < 0x80. Put this in one shared minimal-INTEGER check that
             SSFASN1DecGetInt can use too (see ASN1-3) (recommended)
             (2) Change the .md to say the value is an unsigned magnitude (not recommended).

ASN1-2  Medium  FIXED (2026-11-18)  [demonstrated]
  Location:  ssfasn1.c:84-97 (_SSFASN1ParseTL)
  Problem:   Long-form lengths are not checked for minimality. A length below 0x80 in long
             form is accepted (30 81 03), and so are leading zero length octets
             (30 84 00 00 00 03). X.690 10.1 / 8.1.3.5 require the shortest form in DER. The
             .md says the decoder is DER and "false is returned on any DER malformation".
             ssfecdsa had to add its own strict parser (_SSFECDSASigParseStrictDER, which
             checks "seqLen < 0x80") because this layer does not enforce DER.
  Failure:   30 81 03 02 01 05 -> OpenConstructed true. 30 84 00 00 00 03 02 01 05 -> true.
             One certificate, key or CMS structure can then have many byte encodings that
             all parse. Byte-level identity (fingerprints, dedup, pinning, "is this the same
             cert") no longer matches semantic identity. Every caller also silently accepts
             non-DER input. Signatures still cover the raw tbs bytes, so this is not a
             signature forgery.
  Reach:     Hostile certificate, CMS and key bytes, through every decoder (every decoder
             goes through _SSFASN1ParseTL).
  Evidence:  87    uint8_t numLenBytes = buf[pos++] & 0x7Fu;
             88    if (numLenBytes > 4u) return 0; /* Too large */
             91-96 len = (len << 8) | buf[pos++];   (no minimality check)
             harness: "D Seq 30 81 03 (long form for 3) -> ret=1"
                      "D Seq 30 84 00 00 00 03 -> ret=1 inner=3"
  Options:   (1) After the loop, reject a first length octet of 0x00, and reject
             numLenBytes == 1 with len < 0x80 (equivalently, reject unless
             _SSFASN1LenFieldSize(len) == headerLenBytes) (recommended)
             (2) Document BER-length tolerance and leave strictness to the callers.

ASN1-3  Medium  FIXED (2026-11-18)  [demonstrated]
  Location:  ssfasn1.c:211-224 (SSFASN1DecGetInt)
  Problem:   No INTEGER validation at all. A zero-length body is accepted, and so are
             non-minimal leading 00/FF octets and negative values. md:74-77 gives "an INTEGER
             with non-minimal sign byte" as an example of what returns false.
  Failure:   02 00 -> true, len 0. ssfrsa._SSFRSAPubKeyDecode (ssfrsa.c:259-273) and
             _SSFRSADecIntToBN strip leading zeros and import the bytes as a magnitude. So a
             negative modulus (02 81 80 C0 ...) or a padded one (02 82 01 01 00 00 C0 ...)
             is accepted as an ordinary positive n. ssfx509 checks only the serial number's
             sign and length itself (ssfx509.c:617). It does not check minimality.
  Reach:     Hostile SubjectPublicKeyInfo / RSAPublicKey / RSAPrivateKey / CMS bytes, through
             SSFRSAPubKeyDecode and the ssfx509 parser.
  Evidence:  221   if (!SSFASN1DecGetTLV(cursor, &tag, intBufOut, intLenOut, next)) return false;
             222   if (tag != SSF_ASN1_TAG_INTEGER) return false;
             harness: "C GetInt 02 00 -> ret=1 len=0"
  Options:   (1) Reject an empty body. Reject 00 followed by a byte < 0x80, and FF followed by
             a byte >= 0x80. Leave the sign to the caller, but document that the body is
             two's complement and minimal (recommended)
             (2) Add SSFASN1DecGetUInt, which also rejects negatives, for the key and serial
             callers.

ASN1-4  Medium  FIXED (2026-11-18)  [demonstrated]
  Location:  ssfasn1.c:194-208 (SSFASN1DecGetBool)
  Problem:   Any nonzero byte decodes as true. md:379-380 says DER requires 0xFF / 0x00 and
             that "any other value is rejected" (X.690 11.1).
  Failure:   01 01 01 -> true, val = true. A certificate whose basicConstraints cA or
             extension critical flag is encoded 0x01 is accepted. Other DER parsers reject
             it, so implementations disagree about whether the certificate is valid at all.
  Reach:     Hostile certificate bytes, through ssfx509 (extension critical, ssfx509.c:326;
             basicConstraints cA, ssfx509.c:364).
  Evidence:  205   if (tag != SSF_ASN1_TAG_BOOLEAN || valueLen != 1u) return false;
             206   *valOut = (value[0] != 0x00u);
             harness: "A Bool 01 01 01 -> ret=1 val=1 (md: rejected)"
  Options:   (1) Return false unless value[0] is 0x00 or 0xFF (recommended)
             (2) Correct the .md.

ASN1-5  Medium  OPEN  [demonstrated]
  Location:  ssfasn1.c:255-276 (SSFASN1DecGetBitString)
  Problem:   The unused-bits octet is passed through unchecked. Values above 7 are accepted.
             A nonzero count with an empty payload is accepted. Nonzero padding bits are
             accepted, although DER requires them to be zero (X.690 11.2.1). md:406-409 gives
             the range as 0..7. No caller checks the count: ssfx509 stores pubKeyUnusedBits
             and signatureUnusedBits and never reads them, and the keyUsage parse ignores
             kuUnused.
  Failure:   03 02 08 FF -> true, unused = 8.  03 01 05 -> true, unused = 5, len 0.
             03 02 07 FF -> true with byte FF. Only digitalSignature is declared there, but
             ssfx509.c:388 copies the whole byte into keyUsageBits, so the padding bits read
             as keyEncipherment, keyCertSign, cRLSign and more.
  Reach:     Hostile certificate bytes, through ssfx509 (SPKI, keyUsage, signature).
  Evidence:  272   *unusedBitsOut = value[0];
             273   *bitsOut = &value[1];
             274   *bitsLenOut = valueLen - 1u;
             harness: "E BitString unused=8 -> ret=1 unused=8"
                      "E BitString empty with unused=5 -> ret=1 unused=5 len=0"
                      "E BitString unused=7 byte FF (padding bits set) -> ret=1 byte=FF"
  Options:   (1) Reject value[0] > 7. Reject value[0] != 0 when valueLen == 1. Reject a last
             byte whose low value[0] bits are nonzero (recommended)
             (2) Change only the range check, and make ssfx509 mask the padding bits.

ASN1-6  Medium  OPEN  [demonstrated]
  Location:  ssfasn1.c:759-786 (SSFASN1EncInt); ssfasn1.md:564-566
  Problem:   The .md says the encoder "strips redundant leading sign bytes ... and adds a
             leading 0x00 when the unsigned value's high bit is set". The code copies intBuf
             unchanged. A caller who trusts the .md emits negative or non-minimal INTEGERs.
  Failure:   EncInt({80}) -> 02 01 80 (that is -128). EncInt({00 00 01}) -> 02 03 00 00 01.
             SSFX509 certificate generation passes params->serial straight through
             (ssfx509.c:1790-1791). A serial whose first byte is >= 0x80 is written as a
             negative serial, which SSFX509's own parser then rejects (ssfx509.c:617).
             ssfecdsa and ssfrsa are safe today only because they canonicalize first
             (_SSFECDSACanonicalizeInt, _SSFRSANormalizeMag).
  Reach:     Caller input (certificate generation and any future caller relying on the .md).
             Not reachable from hostile input.
  Evidence:  781   buf[0] = SSF_ASN1_TAG_INTEGER;
             782   _SSFASN1WriteLenField(&buf[1], intLen);
             783   memcpy(&buf[headerLen], intBuf, intLen);
             harness: "J EncInt {80} -> 02 01 80 (md: adds 00)"
                      "J EncInt {00 00 01} -> 02 03 00 00 01 (md: strips)"
  Options:   (1) Fix the .md: intBuf must already be a minimal two's-complement body. Add a
             DBC check for minimality (recommended)
             (2) Add an "unsigned magnitude" encoder that strips zeros and adds the 00, and
             move ssfx509 serial, ssfecdsa and ssfrsa to it.

ASN1-7  Medium  FIXED (2026-11-18)  [demonstrated] [verified 2026-11-18]
  Location:  ssfasn1.c:204-205, 221-222, 268-270, 289-290, 304-305, 320-321, 408-418, 457,
             584-586, 610-612 (all typed decoders); ssfasn1.md:76-77, :372-373
  Problem:   The .md says that on false "*next is not advanced". Every typed decoder calls
             SSFASN1DecGetTLV first, which writes *next. Only after that does it check the
             tag, length or content. A tag mismatch or bad content therefore returns false
             with *next already past the element. Callers often alias next to the cursor,
             as in GetX(&c, ..., &c). In that case a failed decode silently consumes the
             element.
  Failure:   GetBool on 04 01 AA 05 00 -> false, and next is now at offset 3 (past the OCTET
             STRING). In ssfx509.c:324-327 the return of SSFASN1DecGetBool(&extInner,
             &critical, &extInner) is ignored. A critical flag encoded as 01 02 FF FF is
             therefore skipped and critical stays false. A critical extension silently
             becomes non-critical and escapes the unknown-critical-extension rejection.
  Reach:     Hostile certificate bytes, through ssfx509 extension parsing. In general,
             through any caller that trusts the .md's "consumed nothing" guarantee.
  Evidence:  133-134 next->buf = ...; next->bufLen = ...;   (inside GetTLV, before callers'
                                                            tag checks)
             205   if (tag != SSF_ASN1_TAG_BOOLEAN || valueLen != 1u) return false;
             md:77 "On `false` ... `*next` is not advanced"
             harness: "F GetBool on OCTET STRING -> ret=0 next advanced: off=3 len=2"
  Options:   (1) Decode into a local cursor and copy it to *next only on success, in every
             typed decoder (recommended). This also makes aliased calls safe.
             (2) Correct the .md, and separately fix ssfx509.c:326 to check the return value.

Checked, no issue
----------------------------------------------------------------------------------------------
- _SSFASN1ParseTL bounds. bufLen < 2 is rejected. Truncation is checked after the
  high-tag-form extension byte. The "pos + numLenBytes > bufLen" check cannot wrap
  (pos <= 3). Indefinite length (0x80) is rejected. More than 4 length bytes is rejected.
- High-tag form: a continuation bit is rejected (number >= 128), and an extension byte < 31
  is rejected (non-minimal tag number).
- GetTLV overflow-safe subtraction "contentLen > bufLen - headerLen". The next cursor
  arithmetic stays within the buffer. bufLen == 0 is handled before any dereference.
- GetOID: rejects a leading 0x80 on every sub-identifier, rejects a truncated final
  sub-identifier, has a correct 32-bit overflow guard ((arc >> 25) != 0 at byte 5), splits
  the first arc correctly for arc0 = 2 with arc1 >= 40, bounds the output array, and needs
  rawLen > 0.
- Time decoders: exact lengths (13/15/10/19), digit checks, a required 'Z', a year range
  check before the (uint16_t) cast, and month/day >= 1 before the -1. SSFDTimeStructInit
  rejects out-of-range hour/min/sec/day (including Feb 29 off leap years and 2100 as
  non-leap) by returning false. It does not trap, so hostile times cannot halt the device.
- Encoder measure/write consistency. The NULL-buf pass returns the same total as the write
  pass in every encoder. All totals are overflow-guarded against 0xFFFFFFFF.
  bytesWritten = 0 on failure. EncIntU64 keeps intBuf[9] in bounds (at most 8 bytes + 00)
  and uses memmove correctly.
- _SSFASN1LenFieldSize and _SSFASN1WriteLenField agree on every boundary
  (0x7F/0x80/0xFF/0x100/0xFFFF/0x10000/0xFFFFFF/0x1000000), and the encoder always emits
  minimal lengths.
- Time encoders: the year range is enforced (UTCTime <= 2049, ssfdtime <= 2199). The
  unixSec * 1000 multiplication is in a uint64_t SSFPortTick_t and is bounded by
  SSFDTIME_UNIX_EPOCH_SEC_MAX.
- Word size and endianness: there are no size_t or int width assumptions. Every
  multi-byte value is assembled byte by byte. The shifts are on uint32_t/uint64_t, and
  the uint16_t << 8 of a value <= 127 is safe with 16-bit int.
- No recursion and no unbounded loops. Every loop is bounded by bufLen or rawLen.
- Fuzz: 3,000,000 mutated and random inputs under ASan and UBSan, through every decoder,

Checked, no issue
- x509 call sites: every SSFStrLen bound is ub + 1 (<= 255), the value is used only after a
  true return, and the size_t -> uint32_t casts are safe (< 256). The inputs are caller C
  strings, never certificate bytes, so no hostile-input trap or over-read is possible in
  ssfstr.
- SSFStrLen: no read at or past cstr[cstrSize]; cstrSize == 0 -> false with len 0 and no read.
- SSFStrCpy/Cat at an exactly full buffer: srcLen == size-1 (Cpy) or dstLen+srcLen == size-1
  (Cat) succeeds, with the NUL written at size-1. One byte more returns false.
  dstSize == 0 -> false and nothing is written. On every false path, dst and *lenOut are left
  untouched, which matches the "never partially modified" note for Cpy and Cat. On success,
  the result is always NUL-terminated.
- SSFStrCat: dstLen + srcLen cannot wrap for distinct objects. Each length is <= its size - 1,
  and two objects cannot together exceed SIZE_MAX, which also holds for a 16-bit size_t.
- SSFStrCmp: both strings are validated, then compared by length before memcmp. Neither
  string is read past its NUL. Two invalid strings compare unequal.
- SSFStrToCase: modifies the string only after SSFStrLen succeeds, and it touches only bytes
  before the NUL. An invalid enum traps (SSF_REQUIRE), which is correct DBC. The default
  branch is unreachable.
- SSFStrCharToLower/Upper: only ASCII A-Z/a-z are changed. Negative (high-bit) char values
  are returned unchanged, with no UB and no table lookup.
- SSFStrStr matching logic: the restart-at-start+1 backtracking is correct ("subsubstr" and
  the UT fuzz against strstr). substr ends only at a NUL found strictly inside substrSize, so
  *(ss+1) at line 243 is in bounds when sss > 1.
- SSFStrTok: the delimiter scan is bounded by delimsSize, and the delimiters are NUL-stopped.
  The token copy is bounded by the tokenStrSize check, which also leaves room for the NUL.
  tokenStrSize == 0 -> -1 and nothing is written. No global state, so the function is
  re-entrant.
- No endianness or word-size assumptions. No recursion. Every loop is bounded by a size
  counter that strictly decreases. The one exception is SSFStrStr's backtrack, which restores
  cstrSize and then advances by one, so it is still bounded by O(cstrSize * substrSize).
