SSF _crypto CORRECTNESS AUDIT
=============================

Date:        2026-11-18
Branch:      x509 (HEAD a20e458)
Scope:       All modules under _crypto/ (implementation .c/.h and their .md contracts).
             Style, naming and comment issues were out of scope.
Method:      Six parallel reviewers read every line of the implementation files, grouped by
             domain. Where feasible they cross-checked arithmetic against Python big-integer
             references or OpenSSL (ssfbn, ssfpoly1305, ssfx25519, ssfed25519, ssfaesgcm, SHA-2
             constants, EC constants and all six comb tables). The lead reviewer independently
             re-verified every Critical and High finding and the principal Medium findings
             against the source (marked [verified] below). Other findings were quoted with code
             by the reviewer who found them.
Build/test:  MSBuild (v143 toolset) Debug x64 builds clean. Configured unit tests pass:
             ssfcms, ssfx509, ssfbase64url, ssfmatch. The other _crypto unit tests are
             disabled in ssfport.h and were not run under Windows.

Severity scale
  Critical  wrong results, memory corruption or security break in normal use
  High      wrong result on reachable edge cases, undefined behaviour, process halt on
            hostile input where the contract says "returns false"
  Medium    contract/doc mismatch, missing DBC that permits corruption, portability break,
            weakened security margin
  Low       minor correctness nit, latent UB, doc drift

Status values: OPEN, FIXED (date), WONTFIX (reason), DOC (fixed by documentation change)
               The commit for a FIXED item is found with: git log --oneline --grep=<label>

FIX PROCESS (set by Jim 2026-11-18; applies on every machine and every session)
----------------------------------------------------------------------------------------------

  This file is the single tracking document for the audit. Work items strictly in this order:

  1. Jim names the next item by label (e.g. "Tell me about X-1").
  2. Claude gives a concise brief and makes NO code changes: the problem, what it affects, how
     it can manifest, and the options for addressing it (with a recommendation). Where it
     matters, read the current code first; line numbers in this file drift as fixes land.
  3. Jim selects a resolution (he may ask for more detail on an option first).
  4. Claude implements it TDD style:
       a. Add the failing unit test(s) to the module's _ut.c first, in a block whose comment
          names the audit label(s) (e.g. "AUDIT RSA-1/RSA-2"). Base unit tests only; do not
          try to make the OpenSSL-dependent "extended" test paths build on Windows.
       b. Build with the regular Windows build (MSBuild, ssf.sln, Debug x64,
          -p:PlatformToolset=v143 on machines without the project's toolset) and run
          x64\Debug\ssf.exe. Confirm the new test is RED. To run a module's test that is
          disabled in ssfport.h, flip its SSF_CONFIG_<MOD>_UNIT_TEST to 1 temporarily and
          flip it back before committing. Never compile the tree with MinGW gcc/ninja on
          Windows to run tests.
       c. Make the fix following claude.ssf (one-line function header comments, "Is ...?"
          questions before non-trivial conditionals with "Yes, ..." / "No, ..." clause
          comments, parentheses around every sub-expression, one declaration per line, full
          module prefix on private functions, DBC on all parameters, 100-column width,
          spaces not tabs). Do not change other modules (e.g. ssfbn, ssfasn1) to fix a
          dependent module unless Jim approves.
       d. Rebuild and confirm GREEN, including the previously enabled tests (ssfcms and

       e. Update the module's .md if the contract changed.
       f. In this file: change the item's status to FIXED (date), and add a change-log entry
          at the bottom describing what was done and the red/green evidence.
  5. Commit only when Jim asks. Commit message style: "<module>: <summary>" with the audit
     labels mentioned, ending with the Co-Authored-By line the session provides.

  Do not jump straight to a fix for an audit item, and do not batch several items without
  being asked; Jim makes the engineering call on each one.

RSA-1  Critical  FIXED (2026-11-18)  [verified]
  Location:  ssfrsa.c:265 (_SSFRSAPubKeyDecode), :1087-1095, :1112 (SSFRSAVerifyPKCS1),
             :1330-1332, :1347 (SSFRSAVerifyPSS)
  Problem:   The verify entry points never bound the modulus to SSF_RSA_MAX_KEY_BYTES and never
             call _SSFRSAValidatePubFields. The decoder only rejects nl > SSF_BN_MAX_BYTES, which
             is 2x the largest enabled RSA key (SSF_BN_CONFIG_MAX_BITS = 2 x max key bits, so
             1024 bytes with 4096 enabled, the default in _opt/ssfrsa_opt.h). keyBytes is derived
             from the untrusted n; the signature need only be keyBytes long; SSFBNModExpPub,
             SSFBNMontInit, SSFBNMontMul and SSFBNMontSquare only REQUIRE len <= SSF_BN_MAX_LIMBS
             (256), so an 8192-bit modulus passes; SSFBNToBytes then does memset(out, 0, outSize)
             with outSize = keyBytes into uint8_t em[SSF_RSA_MAX_KEY_BYTES] (512).
  Failure:   RSAPublicKey DER with an odd 8192-bit n plus any 1024-byte signature with s < n:
             SSFBNToBytes(&m, em, 1024) overflows em by 512 bytes, then
             memset(&emExpected[2], 0xFF, 970) overflows emExpected. PSS overflows emFull, em and
             dbMask the same way. A 2048-only build (SSF_RSA_MAX_KEY_BYTES 256,
             SSF_BN_MAX_BYTES 512) corrupts the stack on an ordinary 3072/4096-bit certificate.
  Reach:     ssfcms.c:903-906 verifies with the message-embedded signer certificate before chain
             validation (:914-917) and ssfx509.c:2349/:2384 pass keyCert->pubKey straight to
             SSFRSAVerifyPKCS1/PSS with no size check, so a crafted CMS message reaches this.
  Contract:  ssfrsa.md:121 "safe to call on attacker-controlled bytes".
  Evidence:  265   if ((nl == 0u) || (nl > (uint32_t)SSF_BN_MAX_BYTES)) return false;
             1087  keyBytes = (SSFBNBitLen(&n) + 7u) / 8u;
             1088  if (sigLen != keyBytes) return false;
             1070  uint8_t em[SSF_RSA_MAX_KEY_BYTES];
             1095  if (!SSFBNToBytes(&m, em, keyBytes)) return false;
             1112  memset(&emExpected[2], 0xFF, psLen);

X-1  High  FIXED (2026-11-18)  [verified by exact Python model of the routine]
  Location:  ssfx25519.c:157-169 (_fe_mul, second carry fold)
  Problem:   After r = (low + 38*high) mod 2^256 with carry = (low + 38*high) >> 256 (carry can
             be 1..9 for operands < p), the code adds 38*carry to r but discards the final
             carry-out of that addition. Whenever r + 38*carry >= 2^256 the product is wrong by
             exactly -38 mod p (2^256 = 38 mod p). _fe_reduce cannot repair it because the
             information is lost.
  Failure:   a = 0x1813514f909ff4976a8a43ef28804790be6c6fe94c41d9c0f07534feeacc110f
             b = 0x7fcf1dc53b458b5c82005b25087f71e1373278685a16a7bca60df257b59d7433
             (both < p): _fe_mul returns 0x1d; correct a*b mod p = 0x43.
  Reach:     In the first ladder iteration (bit 254 is always set after clamping) A = u+1 and
             B = u-1 are peer-controlled and are squared directly. The reviewer found 292 field
             elements whose square is mis-computed; peer u = s +/- 1 gives 584 peer public keys
             for which SSFX25519ComputeSecret returns true with a WRONG shared secret.
             Example: priv = bytes 0x01..0x20, peer u =
             daa13e72a7eba48d5ea1d6b1d4363d1f5dfbe3c0d83a29721e9a069fc50fdb59
             module: c0f6aeac...e01e  RFC 7748 reference: ee2ba9d0...b27e.
             Honest random inputs hit this with probability ~2^-248 per multiply, so unit tests
             and Wycheproof never see it. Not a key-recovery vector as far as could be seen.
  Fix:       Propagate the final c (0 or 1) once more (one extra fold of 38*c), or let
             _fe_reduce accept a ninth limb.
  Evidence:  uint64_t c = carry * 38u;
             for (i = 0; i < 8u; i++) { c += (uint64_t)r->v[i]; r->v[i] = (uint32_t)c; c >>= 32; }
             _fe_reduce(r);                       /* final c never used */
  Scripts:   scratchpad c25519/femul.py, sqr_search.py, harness_x.c (session scratchpad, may be
             gone; the Python model is trivial to recreate from the C).

E-2  Medium  FIXED (2026-11-18)  [verified: 115 occurrences]
  Location:  ssfed25519.c _sc_reduce and _sc_muladd (e.g. :921, :1070, :1207)

  Fix:       ((int64_t)1 << 20) / ((int64_t)1 << 21). The 2097151u and 666643 literals are fine.
  Evidence:  carry0 = (s0 + (1 << 20)) >> 21; s1 += carry0; s0 -= carry0 * (1 << 21);

             output; the larger size buys no extra security over P-256 / RSA-3072.

             SSFPortGetEntropy for the key bytes, or widen the PRNG seed.
