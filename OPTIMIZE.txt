SSF CODE SIZE AND PERFORMANCE REVIEW
====================================

Date:        2026-11-19
Branch:      x509 (HEAD dbd35d3)
Reviewer:    Claude Opus 5.5 (claude-opus-5-5), single reviewer, modules read sequentially
Scope:       _crypto (all modules, including ssfcms) and _codec ssfstr, ssfmatch, ssfasn1,
             ssfx509. Read in dependency order: ssfstr, ssfmatch, ssfasn1, then the _crypto
             modules from the primitives up, then ssfx509.
Goal:        Find code-size reductions and speed-ups that do not weaken correctness or
             security. Anything that would change constant-time behaviour, input validation,
             DER strictness or an audited fix (AUDIT*.txt) is either excluded or flagged
             with its constraint.

Method
  Size:   gcc 14 -Os -ffunction-sections, x86-64, per-function sizes from nm. No ARM
          cross-compiler is installed; x86-64 -Os .text is a proxy for Thumb-2. It ranks
          functions the same way and is typically 20-40% larger in absolute bytes.
  Speed:  scratchpad benchmark harness (bench.c), -O2 and -Os, x86-64 desktop, median of
          the run. MCU speed-ups are estimated from operation counts where the host figure
          does not transfer (e.g. 64-bit host vs 32-bit limbs).
  Each estimate is "probable": a size figure is the bytes expected to disappear from the
  -Os build, a speed figure is the expected change in the named operation's time.

ID scheme
  <MODULE>-O<n>, e.g. BN-O1. Unique across this file and distinct from the AUDIT labels.

Status:  OPEN, DONE (date), REJECTED (reason)
Effort:  S (< 50 lines), M (50-200 lines), L (> 200 lines or a new algorithm)
Risk:    what must hold for the change to be safe, and the tests that prove it

  Security note raised during the review (not an optimization; see BN-O7): SSFBNMod branched
  on each subtraction's borrow and ssfrsa used it on the blinded value with the secret primes
  p and q. Fixed by BN-O7 (constant-time for odd moduli).

  Suggested order: BN-O1..O3 first (prototyped, small, large measured gain, all suites
  pass), then X509-O1 / CMS-O1 (small, large size win), then BN-O6 (largest Cortex-M win),
  then BN-O5 / BN-O4 for RSA signing, then the Ed25519 group (ED-O1, ED-O3, FE-O1).

ssfstr
----------------------------------------------------------------------------------------------

STR-O1  Speed  OPEN  Effort S
  Where:     SSFStrLen (byte loop)
  Change:    Use memchr(cstr, 0, cstrSize) and take the length from the returned pointer.
             Every SSFStr* function and SSFX509 / SSFMatch callers go through it.
  Probable:  Long strings 4-16x faster with a word-wise libc memchr (glibc, newlib, picolibc
             all have one); short strings unchanged. About -20 B.
  Risk:      Must still return false and *cstrLenOut == cstrSize when no NUL lies within
             cstrSize (current contract). memchr reads at most cstrSize bytes. ssfstr_ut
             covers it.

STR-O2  Size  OPEN  Effort S
  Where:     SSFStrToCase (two copies of the same loop)
  Change:    One loop that calls SSFStrCharToLower or SSFStrCharToUpper chosen before it.
  Probable:  About -50 B. No speed change.
  Risk:      None beyond the existing unit tests.

STR-O3  Speed  OPEN  Effort S
  Where:     SSFStrCmp (SSFStrLen twice, then memcmp: three passes)
  Change:    Single pass comparing bytes and checking both terminators within their sizes.
  Probable:  About 2x faster on equal strings; about -40 B.
  Risk:      Must keep "false if either string is unterminated within its size", including
             when the strings differ before the terminator check. Not timing-sensitive (no
             caller compares secrets with it).

  Reviewed, no change worth making: SSFStrCat / SSFStrCpy (memmove is already the fast path
  and required for overlap, AUDIT STR-7), SSFStrTok, SSFStrStr (restart search is O(n*m) but
  inputs are short and the code is already small).

ASN1-O1  Size  OPEN  Effort S
  Where:     SSFASN1EncUTCTime, SSFASN1EncGeneralizedTime, SSFASN1EncDate, SSFASN1EncDateTime,
             _SSFASN1FormatDate (four inline copies of "two decimal digits" formatting)
  Change:    A static _SSFASN1Put2Digits(dst, v) helper; GeneralizedTime writes
             YYYY MM DD via the helper instead of its own 8 expressions; the four encoders
             share one "convert unixSec, split fields" prologue.
  Probable:  About -500 B of the 1340 B in the four encoders. Encoding speed unchanged
             (not hot).
  Risk:      Byte-identical output; ssfasn1_ut encode vectors cover every form.

ASN1-O2  Size  OPEN  Effort S
  Where:     SSFASN1DecGetTime tail (range checks + SSFDTimeStructInit + StructToUnix)
  Change:    Call the existing _SSFASN1YMDHMSToUnix, which performs the same steps (plus the
             hour / minute / second check SSFDTimeStructInit already makes).
  Probable:  About -150 B.
  Risk:      Keep the far-future branch (AUDIT ASN1-14) ahead of the call. Unit tests cover
             both paths.

ASN1-O3  Size  OPEN  Effort S
  Where:     SSFASN1DecGetOID (two copies of the base-128 sub-identifier loop with the
             non-minimal and 32-bit-overflow checks)
  Change:    One static decoder for a sub-identifier, used for the first and later arcs.
  Probable:  About -120 B.
  Risk:      Same rejections (leading 0x80, > 5 bytes, overflow at the 5th byte). ssfasn1_ut
             OID vectors cover them.

ASN1-O4  Size  OPEN  Effort S
  Where:     SSFASN1DecGetOctetString, DecGetOIDRaw, DecGetNull, DecGetBool, DecGetInt and
             DecOpenConstructed each repeat "GetTLV, compare tag, commit next"
  Change:    A static _SSFASN1DecExpect(cursor, tag, &val, &len, next) that does the common
             part; each public function keeps its own extra checks.
  Probable:  About -150 to -250 B.
  Risk:      Preserve "advance only on success" (AUDIT ASN1-7) in every function.

  Reviewed, no change worth making: _SSFASN1ParseTL and SSFASN1DecGetTLV are already minimal
  and every check in them is a DER rule from the AUDIT files; the encoders' two-pass
  measure / write design is what keeps them allocation-free.

ssfsha1
----------------------------------------------------------------------------------------------

SHA1-O1  Speed  OPEN  Effort S
  Where:     SSFSHA1Update (one byte at a time into ctx->block, with a length check per byte)
  Change:    Same chunked memcpy loop SSFSHA2_32Update uses; hash whole 64-byte blocks
             straight from the input when the buffer is empty.
  Probable:  1.3-1.6x on long inputs (the per-byte loop costs about as much as the compression
             on a Cortex-M). About -20 B.
  Risk:      Keep the SHA1-MAX length REQUIRE once per call. ssfsha1_ut multi-chunk vectors
             cover split updates.

SHA1-O2  Speed + stack  OPEN  Effort S
  Where:     _SSFSHA1ProcessBlock (80-word schedule array; one loop with a 4-way branch per
             round)
  Change:    16-word circular schedule (w[t & 15]) and four 20-round loops, each with its own
             f / K. The wipe shrinks from 320 B to 64 B per block.
  Probable:  Stack -256 B. Speed 1.2-2x: measured -O2 is 2.1x slower than -Os here (85 vs
             40 us per 16 KB), which points at the per-round branch defeating the compiler;
             fixed loops remove it at every optimization level.
  Risk:      None functional; keep the SHA1-2 scrub (now of the 16-word ring).

ssfsha2
----------------------------------------------------------------------------------------------

SHA2-O1  Speed + stack  OPEN  Effort S
  Where:     _SSFSHA2_32Block (w[64]), _SSFSHA2_64Block (w[80] of uint64_t)
  Change:    16-word circular message schedule computed inside the round loop.
  Probable:  Stack -192 B (SHA-256) and -512 B (SHA-512); the per-block wipe shrinks the same
             way (64 -> 16 and 160 -> 32 word stores on a 32-bit target). Speed +5-10%.
  Risk:      Keep the SHA2-3 scrub of the (smaller) schedule. FIPS vectors in ssfsha2_ut.

SHA2-O2  Size  OPEN  Effort S
  Where:     SSFSHA2_32Begin, SSFSHA2_64Begin (IVs written as 8 or 32 immediate assignments)
  Change:    static const IV tables (2 x 8 words, 4 x 8 double-words) and one memcpy.
  Probable:  About -400 B (SSFSHA2_64Begin is 512 B, SSFSHA2_32Begin about 170 B). No speed
             change.
  Risk:      None; vectors cover every variant.

SHA2-O3  Speed  OPEN  Effort S
  Where:     SSFSHA2_32Update / SSFSHA2_64Update (every byte copied into the context buffer)
  Change:    When the buffer is empty, compress full blocks straight from the input.
  Probable:  +2-4% on long inputs (saves one 64 / 128-byte memcpy per block).
  Risk:      The block function reads its input with byte loads (GETU32BE), so unaligned input
             is already safe.

ssfhmac
----------------------------------------------------------------------------------------------

HMAC-O1  Speed  OPEN  Effort M
  Where:     SSFHMACBegin / SSFHMACEnd (outer pad block hashed again for every message)
  Change:    At Begin, also absorb oKeyPad into a second hash context and store that state in
             place of oKeyPad; End copies it and adds only the inner digest.
  Probable:  One compression saved per HMAC: about 25% faster for short messages (4 -> 3
             compressions), which is the common case (HKDF, HMAC-DRBG in RFC 6979 signing,
             TLS 1.3 key schedule). Context grows by about 90 B (a SHA-512 state replaces the
             128-byte pad).
  Risk:      The stored state is key-derived; DeInit already wipes the whole context.

HMAC-O2  Speed  OPEN  Effort M
  Where:     callers that MAC many messages under one key (SSFHKDFExpand loop, RFC 6979 in
             ssfecdsa)
  Change:    Keep a copy of the post-ipad state so a new message under the same key starts
             from it (an SSFHMACReset or context-copy helper).
  Probable:  With HMAC-O1, 2 compressions per short MAC instead of 4: about 2x for repeated
             MACs. RFC 6979 runs at least 6 HMACs per ECDSA signature, but signing is
             dominated by the scalar multiply, so the effect there is a few percent.
  Risk:      New API surface; the copied state must be wiped by the caller's DeInit.

HMAC-O3  Size  OPEN  Effort S
  Where:     _SSFHMACGetBlockSize, SSFHMACGetHashSize, and the four dispatch switches
  Change:    Two small const tables indexed by hash; keep the switches only where they call
             different functions.
  Probable:  About -80 B.
  Risk:      Keep the range REQUIRE on hash before indexing.

ssfaes, ssfaesctr, ssfaesccm
----------------------------------------------------------------------------------------------

  No findings worth the risk. AES-128 runs about 73 ns per block on the host (byte S-box,
  word MixColumns). A T-table implementation would be 2-3x faster but adds 1-4 KB of tables
  and data-dependent loads over more memory (a larger cache-timing surface): REJECTED on
  security grounds. CTR and CCM already expand the key once per call.

ssfaesgcm
----------------------------------------------------------------------------------------------

  Measured split (16 KB, -O2): AES-CTR 75 us, GHASH 70 us, so GHASH is about half of GCM.

GCM-O1  Speed  OPEN  Effort S
  Where:     _SSFAESGCMBlockMult (H bit-reversed and loaded every block; Karatsuba operand
             sums of H recomputed every block)
  Change:    Prepare H once per message (reversed words plus the y0^y1, y2^y3, y0^y2,
             y1^y3 and four-way sums), pass the prepared form to the block multiply.
  Probable:  GHASH +15-20% (removes 4 of the 8 ReverseBytes per block and 5 XOR groups);
             GCM overall +7-10%.
  Risk:      The prepared H is key-derived: wipe it at the end of Encrypt / Decrypt.

GCM-O2  Speed  OPEN  Effort S
  Where:     _SSFAESGCMBlockMult (six SSFCryptSecureZero calls, 28 words, per 16-byte block)
  Change:    Hold the multiply's temporaries in _SSFAESGCMGHASH's frame and wipe them once
             after the loop.
  Probable:  GHASH +10%.
  Risk:      Same scrub guarantee (wiped before the function returns); the GCM-3 scrub test
             hook must observe the new wipe.

ssfbn
----------------------------------------------------------------------------------------------

  BN-O1, BN-O2 and BN-O3 were prototyped together on a scratchpad copy of ssfbn.c (the
  repository is unchanged). With all three, ssfbn, ssfrsa, ssfec, ssfecdsa, ssfx509 and
  ssfcms unit tests pass. Measured (x86-64 -O2):

    Primitive (2048-bit)      before      after          End to end          before   after
    SSFBNMontInit             321 us      27 us          RSA-2048 verify     449 us   87 us
    SSFBNMontMul              3.85 us     3.09 us        RSA-2048 sign      7710 us  5380 us
    SSFBNMontSquare           5.21 us     2.43 us        ECDSA P-256 sign    370 us   335 us
    SSFBNModInv (Fermat, 256) 54.4 us     32.5 us        ECDSA P-384 sign    793 us   649 us

BN-O1  Speed  DONE (2026-11-19)  Effort S  [implemented, red/green]
  Where:     SSFBNMontInit (R^2 mod m by 2 * len * 32 modular doublings: 4096 SSFBNModAdd
             calls for a 2048-bit modulus, on every RSA verify, every CRT half of every RSA
             sign, every Fermat inverse and every Miller-Rabin candidate)
  Change:    Start at 2^(L-1) (L = bit length of m), double (w - L + 1 + j) times to reach
             2^(w + j) mod m, where w = 32 * len = j * 2^s with j odd, then s Montgomery
             squarings (each doubles the exponent offset): 2048-bit is 2 doublings and 11
             squarings.
  Probable:  MontInit 12x faster. RSA-2048 verify 2.6x on its own (449 -> 170 us measured).
             Fermat inverses (ECDSA sign k^-1, every EC affine conversion) about 40% faster.
             RSA keygen faster (MontInit per candidate). No size change.
  Risk:      The doubling count depends on L, the modulus bit length, which is public for an
             RSA modulus and fixed by the key size for its primes; every operation is still
             the CT ModAdd / MontSquare. Bit-exact R^2 is checked by every Montgomery test in
             ssfbn_ut, ssfrsa_ut and the EC suites.

BN-O2  Speed  DONE (2026-11-19)  Effort S  [implemented, red/green]
  Where:     SSFBNMontMul (after each row's reduction, a separate n+1-word shift loop moves
             t down by one word: n^2 extra loads and stores)
  Change:    Standard CIOS: the reduction loop writes t[j - 1] directly, so the shift is
             fused and the separate loop disappears.
  Probable:  MontMul +25% (3.85 -> 3.09 us measured at 2048 bits). Smaller code.
  Risk:      Fixed-length loops, no data-dependent branch: constant-time behaviour unchanged.

BN-O3  Speed  DONE (2026-11-19)  Effort S  [implemented, red/green]
  Where:     SSFBNMontSquare: step 3 propagates each diagonal term's carry to the end of t
             (sum over i of 2n - 2i iterations, about n^2), and the SOS reduction propagates
             each row's carry to t[2n] (about n^2 / 2). Both were made fixed-length for
             constant time (AUDIT BN-12), so they cost as much as the multiplies.
  Change:    Step 3 as one pass with a running carry; the reduction keeps a one-word
             deferred carry that the next row adds at t[i + n] (no later row writes there
             first). Both remain fixed-length, so still constant-time, and become O(n).
  Probable:  MontSquare 2.1x (5.21 -> 2.43 us measured). With BN-O1 and BN-O2: RSA-2048
             verify 5.2x (449 -> 87 us), sign 1.43x (7.7 -> 5.4 ms).
  Risk:      Carry correctness: the deferred carry is at most 1 and the final t[2n] bound is
             unchanged (< 2m). Covered by every Montgomery vector; add a randomized
             MontSquare == MontMul(a, a) cross-check to ssfbn_ut when implementing.

BN-O4  Speed  DONE (2026-11-19)  Effort M  [with BN-O5; measured under BN-O5]
  Where:     SSFBNModMulCT (fixed 32n + 1 rounds of a 2n-limb subtract, select and
             shift-right-by-one: about 190 n^2 limb operations; 283 us at 2048 bits). RSA
             signing calls it 3 times (blinding c * r^e, CRT recombination h * qInv, unblinding
             m * r^-1); ECDSA signing twice at 256 bits; SSFBNModInv's final check once.
  Change:    For odd m (every caller): r = MontMul(MontMul(a, b), R^2) with a Montgomery
             context; keep the shift-subtract path for even m.
  Probable:  2048-bit: 283 us -> about 35 us with the context set up (BN-O1 makes MontInit
             cheap), about 30 us less again when the caller already has the context. RSA
             sign -0.6 to -0.7 ms (about -12% after BN-O1..O3). ECDSA sign a few percent.
  Risk:      MontMul requires a->len == b->len == m->len and a, b < m (the BN-10 precondition
             ModMulCT already documents). Constant-time: MontMul is CT.

BN-O5  Speed  DONE (2026-11-19)  Effort M  [with BN-O4]
  Where:     SSFBNModInvExt (extended Euclid built on SSFBNDivMod, which is bit-serial: 2.2 ms
             at 2048 bits, 44 us at 256 bits). RSA signing calls it once for the blinding
             inverse r^-1 mod n: after BN-O1..O3 that is about 40% of RSA-2048 sign time.
  Change:    Binary extended GCD for odd moduli (shifts and subtracts only, no division),
             or obtain r^-1 without a general inverse: compute r^-1 mod p and r^-1 mod q by
             Fermat in the CRT halves (two half-size exponentiations, CT) and recombine.
  Probable:  Binary xgcd 4-6x faster (2.2 ms -> 0.4-0.5 ms): RSA-2048 sign about -1.8 ms
             (5.4 -> about 3.6 ms; with BN-O4 about 3 ms, 2.5x better than today). ECDSA
             verify about -35 us (-3%).
  Risk:      ModInvExt is documented as variable-time; RSA uses it on the random blinding
             factor r (AUDIT RSA-9 accepted that timing). A binary xgcd is also variable-time
             in its inputs, so this does not change the accepted exposure. The Fermat-in-CRT
             alternative is CT if constant-time behaviour is wanted.
  Prototype (scratchpad; ssfbn, ssfrsa, ssfec, ssfecdsa, ssfx509, ssfcms tests pass):
             BN-O4: SSFBNModMulCT dispatches odd m to MontMul(MontMul(a, b), R^2) and keeps
             the shift-subtract body for even m (and keeps the AUDIT BN-1 "a < m or b < m"
             REQUIRE). BN-O5: SSFBNModInvExt dispatches odd m with 0 < a < m to a binary
             extended GCD (u, v, x1, x2; halving mod m; subtract the smaller) and keeps the
             Euclid body for even m (RSA keygen's d = e^-1 mod lambda) and other inputs. Both
             old bodies move to static helpers so the fast paths do not zero-fill their
             buffers.

             Cortex-M0+ 17171 -> 16572 B (-599), mostly SSFBNModMulNIST (the reductions are

BN-O7  Speed  DONE (2026-11-19)  Effort M
  Where:     SSFBNMod (bit-serial shift-and-subtract; 55 us for 2048 mod 1024, 230 us for
             4096 mod 2048), used for the RSA CRT split cB mod p, cB mod q, in key checks,
             and by SSFBNModMul (ECDSA verify u1, u2).
  Change:    For odd m, reduce with Montgomery: split x = xH * 2^w + xL, then
             x mod m = MontMul(xH mod m, R^2) + xL mod m, each "mod m" a single conditional
             subtraction because xH, xL < 2m for a full-width m.
  Probable:  RSA sign -0.1 ms; ECDSA verify -5 us. Small, but it also removes a branch on
             secret data (below).
  Risk:      Needs a full-width (top bit set) m for the one-subtraction bound; keep the
             generic path for other m.
  Security note (not an optimization): SSFBNMod branches on each step's borrow
             ("if (borrow != 0u) add shifted back"). ssfrsa calls it with the secret primes
             p and q on the blinded value cB. Blinding randomizes cB, which limits what the
             timing reveals, but the branch pattern still depends on p. BN-O7's CT form
             would remove it. Worth confirming against AUDIT RSA-9's accepted-timing scope.

  Change:    Let the curve parameters carry the reduction to use (a field id) and call it

ssfec
----------------------------------------------------------------------------------------------

  Field arithmetic is the cost: a variable-base P-256 multiply (ECDH, the u2 * Q half of
  verify) is about 256 doublings and 78 additions, about 3300 field multiplies and 3600
  field adds. BN-O6 and BN-O8 are the main levers; the items below are smaller.

EC-O1  Speed  OPEN  Effort S
  Where:     _SSFECPointDouble, _SSFECPointAdd* (squares computed with SSFBNModMulNIST(x, x))
  Change:    A squaring entry (SSFBNSquare + NIST reduction): n(n+1)/2 instead of n^2 limb
             products.
  Probable:  About 40% of the field multiplies in a doubling-heavy scalar multiply are
             squares: ECC +8-12%.
  Risk:      SSFBNSquare must stay free of operand-dependent shortcuts. It was not: its
             diagonal carry loop was a while (carry != 0); fixed first (SQ-CT, 2026-11-19).
  Measured (prototype, 2026-11-19): 18 square sites in ssfec (not 7). The product is only
             15-20% of SSFBNModMulNIST; squaring trims it 25-35%, so P-256 verify / ECDH
             gain 7-8% on emulated ARM32 and 1-4% on x86-64, P-384 1-3%, sign within noise.
             Code +66 B Cortex-M4 (ssfbn + ssfec). The NIST reduction dominates: see EC-O4.

EC-O4  Speed  DONE (2026-11-19)  Effort M  [found while measuring EC-O1]
  Where:     _SSFBNReduceP256 / _SSFBNReduceP384: 9 / 10 fold passes, then a constant-time
             correction that always runs 23 full passes (an add or subtract plus a masked
             select each: 8 + 12 + 3 for P-256, 6 + 14 + 3 for P-384) sized for worst-case
             carries, where about 4-7 are needed. Reduction and overhead are about 85% of a
             field multiply (P-256: 193 of 227 ns x86-64, 910 of 1110 ns ARM32).
  Change:    Fold the net signed carry (about -4..+7) in one constant-time step using the
             prime's special form, then one or two conditional subtractions: about 15
             pass-equivalents instead of about 55.
  Probable:  Reduction 3-4x, field multiply about 2-2.5x, ECDSA / ECDH probably 1.5-2x (to
             be confirmed by a prototype). Code about the same or smaller.
  Risk:      Must stay constant-time; needs a written carry-range argument, a differential
             against the current reductions, and boundary vectors near p, 2p and the
             folding limits.

EC-O2  Speed  OPEN  Effort S
  Where:     SSFECPointToAffine (SSFBNModInv Fermat: MontInit plus a 256-bit exponentiation
             per call)
  Change:    Precompute the Montgomery constants of p and n in the curve parameters, so the
             inverse skips MontInit (after BN-O1 this saves about 5 us per call, less than
             before).
  Probable:  ECDSA sign / ECDH -1-2% after BN-O1.
  Risk:      Constant tables; check them against MontInit in the unit tests.

EC-O3  Stack + speed  DONE (2026-11-19)  Effort M  (found while measuring BN-O6)
  Where:     the curve-width modular arithmetic ssfec / ssfecdsa run through the 8192-bit-cap
             ssfbn paths: SSFECPointToAffine and ECDSA k^-1 use SSFBNModInv (Fermat:
             SSFBNModExp -> SSFBNModExpMont with a 16-entry table of SSF_BN_MAX_LIMBS-limb
             values, 10.4 KB on Cortex-M4); ECDSA verify uses SSFBNModInvExt and SSFBNModMul
             (several 1 KB locals each).
  Change:    Curve-width versions: a Fermat inverse for p and n through SSFBNModMulNIST /
             Montgomery at 8 or 12 limbs with a fixed addition chain or a small window, and
             mod-n multiply / inverse with locals sized SSF_EC_MAX_LIMBS.
  Probable:  With BN-O6, call-graph peaks (Cortex-M4) fall from about 18 KB to about 7-10 KB:
             ECDSA sign 18392 -> about 8300 B, ECDH 18016 -> about 7250 B, keygen 17504 ->
             about 7260 B, verify 18256 -> about 10000 B. Speed: Fermat inverses at curve
             width, a few percent.
  Risk:      The inverses take secret inputs (k, Z of a secret multiple): they must stay
             constant-time, as SSFBNModInv is today. Needs new tests at both curves.
  Prototype (scratchpad, 2026-11-19; ssfbn, ssfrsa, ssfec, ssfecdsa, ssfx509, ssfcms tests
             pass): SSFBNModInvSmall (Fermat a^(m-2) mod m in Montgomery form at <= 12 limbs,
             4-bit window; the exponent is public, so the table is indexed directly and the
             operation sequence never depends on the secret base; a * r == 1 checked as
             today) and SSFBNModMulSmall (MontMul(MontMul(a, b), R^2)), used for
             SSFECPointToAffine's Z^-1, ECDSA sign's k^-1 and both SSFBNModMulCT calls, and
             verify's SSFBNModInvExt and both SSFBNModMul calls.
  Measured:  Stack, Cortex-M4 reachable call-graph peaks (excluding SSFBNModMulNIST's generic
             fallback and SSFBNMul's Karatsuba path, neither reachable at 8 / 12 limbs):
             ECDSA sign 18392 -> 6120 B, verify 18256 -> 7832 B, ECDH 18016 -> 5640 B, keygen
             17504 -> 5128 B. The scalar multiplies are now the deepest chains. New frames:
             SSFBNModInvSmall 1216 B (against SSFBNModInv 2088 B + SSFBNModExpMont 10440 B).
             Code: SSFBNModInvSmall 480 B, SSFBNModMulSmall 168 B on Cortex-M4 (460 / 164 B on
             M0+). In a linked Cortex-M4 image using ECDSA + ECDH but not RSA (gc-sections,
             newlib-nano): 43972 -> 42108 B (-1864 B), because SSFBNModExpMont,
             SSFBNModInvExt and SSFBNModMulCT are no longer linked. With RSA also linked they
             stay, so the net is about +650 B.
             Speed, x86-64 -O2: P-256 sign 322 -> 283-298 us (-8 to -12%), P-384 sign 600 ->
             565 us (-6%), verify and ECDH within noise. Emulated ARM32: P-384 sign 4235 ->
             3783 us (-11%), P-256 sign, verify and ECDH within 1-2%.

  Reviewed, no change worth making: the 4-bit fixed-window CT variable-base multiply (a
  signed 5-bit window saves about 10 additions of 334 point operations: 3%), the comb
  tables (already configurable via SSF_EC_FIXED_BASE_COMB_H and FIXED_BASE_P256 / P384).

ssfrsa
----------------------------------------------------------------------------------------------

  Every significant RSA cost is in ssfbn (BN-O1 to BN-O5, BN-O7). Measured profile of
  RSA-2048 sign after BN-O1..O3: modular exponentiations about 2 ms, ModInvExt 2.2 ms,
  ModMulCT 0.6 ms, SSFBNMod 0.1 ms. Projected with BN-O4 and BN-O5: about 2.5-3 ms, against
  7.7 ms today.

RSA-O1  Stack  OPEN  Effort M  (superseded by RSA-STK below, which measures and extends it)
  Where:     SSFRSAKeyGen, SSFRSAPrivKeyIsValid, _SSFRSAPrivKeyDecode callers (10-15 locals at
             SSF_BN_MAX_LIMBS each, 1 KB apiece at the default cap, all zero-filled per call)
  Change:    Size working values at SSF_BN_MAX_MOD_LIMBS (the modulus width) where they never
             hold a double-width product, as _SSFRSAPrivateOpCRT already does.
  Probable:  Several KB less stack and zero-fill per call; speed effect small next to the
             exponentiations.
  Risk:      Each resized local must be shown never to hold a 2n-limb product.

RSA-STK  Stack  Phase 1 DONE (2026-11-19), Phase 2 OPEN  Effort M  [both measured]
  Where:     RSA signing and key generation peak at about 36 KB of stack on Cortex-M4 in the
             default (RSA-4096 capable) build. Deepest signing chain, measured: SSFRSASignPKCS1
             12.0 KB (11 locals at SSF_BN_MAX_LIMBS, 1 KB each, holding at most modulus-width
             values) > _SSFRSAPrivateOpCRT 10.1 KB (17 locals at modulus width, 9 of them
             prime-sized) > SSFBNModExp 2.1 KB (its Montgomery context at SSF_BN_MAX_LIMBS) >
             SSFBNModExpMont 10.4 KB (16-entry window table) > ConvertOut / MontMul 2.2 KB.
  Phase 1:   Size every local to its real width: Montgomery contexts and scratch at
             SSF_BN_MAX_MOD_LIMBS (the documented bound on SSFBNMont_t::len) in ModExp,
             ModExpPub, ConvertOut, MontMul, MontSquare and IsProbablePrime; in RSA sign, PSS,
             keygen and the CRT op, n-width values at SSF_RSA_MAX_KEY_BITS and prime-width
             values at half that (blinded CRT exponents at half + 2). The CRT's double-width
             recombination product is left at the cap.
             Prototype: all 8 suites pass, normal and ASan + UBSan. Speed neutral (RSA-2048 sign
             x86-64 2668-3030 -> 2716-2752 us, emulated ARM32 15918 -> 15512 us). Code
             (ssfbn + ssfrsa, arm-none-eabi-gcc -Os): +70 B Cortex-M4, +100 B Cortex-M0+.
  Phase 2:   Smaller window table in SSFBNModExpMont. SSF_BN_MODEXP_WIN_K must divide 32, so a
             3-bit window is not an option (an earlier estimate assumed one). Choices: the
             existing option SSF_BN_MODEXP_WIN_K = 2 (4-entry table, no code change), measured
             +12% RSA-2048 sign time on x86-64 and +15% on emulated ARM32; or signed 4-bit
             digits (8-entry table with constant-time negation), about today's speed, which
             needs code and is computed here rather than measured (8 entries x 512 B fewer at
             the default cap, x 256 B in an RSA-2048-only build).
  Measured:  Reachable call-graph peaks on Cortex-M4 (the old Euclid / shift-subtract bodies,
             unreachable for signing's odd moduli, excluded), RSA-2048 PKCS#1 sign / PSS sign:
               default build, window 4:  35.9 / 36.6 KB -> Phase 1 24.9 / 25.6 KB
               default build, window 2:  29.8 / 30.6 KB -> Phase 1 18.8 / 19.6 KB
               RSA-2048-only, window 4:  18.4 / 18.9 KB -> Phase 1 12.9 / 13.4 KB
               RSA-2048-only, window 2:  15.3 / 15.8 KB -> Phase 1 10.6 / 11.1 KB
             Signed 4-bit digits (computed): Phase 1 + 8-entry table about 20.9 KB default,
             about 10.9 KB RSA-2048-only.
             Key generation (static peak): default 35.7 -> 26.5 KB (window 4), 29.6 -> 22.8 KB
             (window 2); RSA-2048-only 18.2 -> 13.6 / 15.7 -> 13.3 KB. Its peak goes through the
             Euclid inverse over the even lambda(n) (9.4 KB frame), which Phase 1 does not yet
             resize. Verify: default 12.4 -> 10.4 KB.

  2026-11-19  BN-O1 DONE. SSFBNMontInit starts at 2^(L-1), L = bit length of m, runs
              w - L + 1 + j SSFBNModAdd doublings to 2^(w + j) mod m (w = 32 * len = j * 2^s,
