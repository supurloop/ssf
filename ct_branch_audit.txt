SSF CONSTANT-TIME HELPERS: SECRET-DEPENDENT BRANCHES IN COMPILED CODE (ARMv6-M)
===============================================================================
Audit date : 2026-11-27
Scope      : constant-time select / swap helpers in _crypto, as compiled (not as written).
             Code at commit c0d17b7 (branch mqtt). arm-none-eabi-gcc 15.2, -mthumb -Os.
Status     : C1 FIXED, C2 FIXED (results below), C3 OPEN (C1 found during RSA-PERF R4 step 0; C2 found by the C1 step 1
             check). Step 1 of the C1 plan is done; see STEP 1 RESULTS.

FINDING
-------
C1. Mask-select helpers compile to a branch on the secret flag on Cortex-M0 / M0+ / M23 FIXED
    The C is correct mask arithmetic:
      SSFBNCondCopy    dst = (src & mask) | (dst & ~mask),  mask = -(sel != 0)
      SSFBNCondSwap    d = (a ^ b) & mask; a ^= d; b ^= d
      SSFFE25519CSwap  the same, with mask = -(swap & 1)
    GCC sees that mask is 0 or all ones and, on ARMv6-M (no IT instruction, so no
    conditional move), emits a real branch on the flag inside the per-limb loop. In the
    disassembly of SSFBNCondCopy (M0+ -Os):
        ldr   r1, [r4, r3]   ; dst[i]
        ands  r1, r2
        cmp   r6, r7         ; r6 = (sel != 0)
        beq.n skip           ; sel == 0: skip the src load and the orr
        ldr   r7, [r5, r3]   ; src[i]
        orrs  r1, r7
      skip:
        str   r1, [r4, r3]
    SSFBNCondSwap and SSFFE25519CSwap: "cmp r2, #0; beq" on the swap flag, per limb.
    The selected and unselected cases run different instruction counts, so the timing
    gives the flag away.

    Per core (-Os):
      Cortex-M0 / M0+ / M23 (ARMv6-M, v8-M Baseline): BRANCH: not constant time.
      Cortex-M3 / M4 (ARMv7-M / v7E-M): IT-block conditional moves (it eq; moveq). The
        loads always run, and a skipped IT instruction still takes its cycle, so these are
        constant time as compiled. (M7 / M33 not yet checked.)

    Secrets exposed on ARMv6-M:
      - RSA private key: _SSFBNModExpMontCore picks one of 2^K table entries per K-bit
        exponent window with SSFBNCondCopy(sel = (i == w)). That gives away the windows of
        the CRT exponents. (RSA-PERF R4 replaces this select with a branch-free fused loop
        and removes this case; the helpers below stay.)
      - X25519: Montgomery ladder, SSFFE25519CSwap on secret scalar bits (ssfx25519.c:227,
        228, 255, 256).
      - Ed25519: _SSFEd25519GeCSwap -> SSFFE25519CSwap in the scalar multiply
        (ssfed25519.c:508); secret where the scalar is (signing).
      - ECC: ssfec point-add fix-ups (ssfec.c:334-348, 447-461), SSFBNCondCopy with flags
        derived from intermediate points (degenerate cases of a secret-scalar multiply).

    Why tests miss it: the results are right either way. Only the compiled code is wrong,
    and only on cores the host and qemu-arm (armv7-a) suites do not build for.

    Proposed fix (not started):
      1. A value barrier on each mask before use: on GCC / Clang,
         __asm__("" : "+r"(mask)), which hides the value from the optimizer so it cannot
         prove the mask is 0 or all ones; elsewhere a volatile read. One macro in ssfport.h
         next to SSF_OPTIMIZER_BARRIER (which takes a pointer, not a value).
      2. Find every helper of this kind in _crypto (select, swap, cmov, conditional add /
         sub with a mask, table lookups) and apply it.
      3. A check script: build _crypto for cortex-m0plus, m3, m4, m33 at -Os and -O2, and
         fail if a listed constant-time function has a conditional branch or IT block
         outside its loop control. TDD: the script is red on c0d17b7 for M0+.
      4. Measure the cost: a barrier can stop some instruction scheduling; expect a small
         effect, in instructions only.

----------------------
Goal: no constant-time function in _crypto takes a branch, or runs a different
instruction sequence, depending on secret data, on any supported ARM core, as compiled.
A check that runs in CI-style scripts enforces this, so a compiler change cannot bring the
bug back unnoticed.

STEP 1 RESULTS (2026-11-27, code at fc6a14f)
--------------------------------------------
The check: a scratch tool (session scratchpad, ctcheck/), not committed.
  - driver.c: 32 cases, each called 3-5 times between ct_begin() / ct_end() markers, with
    inputs that differ only in the secret.
  - run.sh / all.sh: build every compiler x core x -O.
  - cmpstream.py: streams the qemu -d exec,nochain trace. Each call gets a rolling hash of
    its PC sequence and a per-PC count. A case fails if its calls' hashes differ; the PCs
    whose counts differ are mapped to source lines with addr2line.
  The driver is built at -O0 (one call site per case), the code under test at the level
  under test. The whole matrix (20 builds) takes about 50 s on 24 cores.
  Public-data allowances: the trace is not compared inside SSFEd25519Verify or
  SSFECDSAVerify (verify-after-sign runs on the public signature), from their entry to
  their bl return site. ECDSA sign keys are picked outside the measured region so that
  every signature has the same DER shape (the encoding of the public r and s).
  Cases:
    ssfbn: CondCopy, CondSwap, Cmp, Add, Sub, ModAdd, ModSub, IsZero, IsOne, MontMul,
           MontSquare, MontConvertIn / Out, ModMulCTOdd, ModMulSmall, ModMulNISTPrime,
           ModInvCT, ModInvSmall (8-limb P-256 prime), ModExp (secret exponent, 4 limbs)
    ssffe25519: CSwap, Reduce, ToBytes, Mul, Inv
    SSFCryptCTMemEq, SSFPoly1305Mac (secret key), SSFX25519ComputeSecret,
    SSFEd25519PubKeyFromSeed / Sign, SSFECDHComputeSecret / SSFECDSAPubKeyFromPrivKey /
    SSFECDSASign (P-256; the last two use the fixed-base comb)
  Red as expected: SSFBNCondCopy, SSFBNCondSwap and SSFFE25519CSwap fail on M0+ with GCC
  -Os and pass on M4, the known positives.

Result by core (both compilers, -Os and -O2):
  Cortex-M3 / M4 / M33: all 32 cases pass (gcc and clang, -Os and -O2).
  Cortex-M0+ / M23: 21-22 of 32 fail with each compiler. Root causes:

  C1 (compiled branches in our code), compiler by compiler:
    SSFBNCondCopy                   gcc and clang, -Os and -O2
    SSFBNCondSwap                   gcc and clang, -Os and -O2
    SSFFE25519CSwap                 gcc -Os / -O2, clang -Os
    _SSFBNRawCmp (ssfbn.c:220-221, "a[i] > b[i]" compares)          clang
    SSFBNMontMul (:3282) / MontSquare (:3402), final conditional
      subtract "(borrow != 0u) & (t[n] == 0u)"                       clang
    _SSFBNS30AddIfNeg (:2234, safegcd)                               clang
    _SSFBNModMulNISTFast (:2692, final masked select)                clang -Os
    _SSFBNModExpSelect (R4's new select)                             clang -O2
  The R4 select is branch-free with GCC (checked in R4) but not with clang -O2, so R4's
  "fixes the RSA case" holds for GCC only, until C1's barrier is in.
  Every one is the same pattern: a 0 / all-ones mask (or a 0 / 1 compare) that the
  optimizer can see, which a core without IT / conditional moves turns into a branch.

C2. libgcc __muldi3 (64-bit multiply) is variable time on ARMv6-M / v8-M Baseline  FIXED
    Cortex-M0 / M0+ / M23 have no 32x32 -> 64 multiply instruction. Every
    (uint64_t)a * b in the code, with GCC and with clang (both link libgcc here), becomes
    a call to __aeabi_lmul -> __muldi3. That builds the product from 16-bit halves with
    the generic C of longlong.h, whose carry fix-up is a branch (libgcc2.c:532,
    "if (x1 < x2) x3 += B"). So every big-number and curve25519 multiply is variable time
    on these cores: MontMul / MontSquare (the row kernel), FE25519 Mul / Inv, and
    everything above them (RSA, ECDH, ECDSA, X25519, Ed25519). It is a cause in 18 of the 21
    failing cases with gcc -Os on M0+ (17 of 22 with clang). It is not in SSF's source, so C1's barrier cannot fix it.
    Fix options (not started):
      (a) A constant-time 32x32 -> 64 helper for targets without UMULL (__ARM_ARCH_6M__,
          __ARM_ARCH_8M_BASE__): four MULS on 16-bit halves, with carries done
          arithmetically. Use it in the row kernel (the R2 macro's C branch) and in
          ssffe25519 / ssfed25519 / ssfpoly1305 wherever a 64-bit product is formed.
          Speed: about the same as __aeabi_lmul (R1 measured a 16-bit-halves C kernel
          at -12.1% on M0+ RSA sign), so likely no cost, possibly a gain.
      (b) R7 (an ARMv6-M assembly row kernel) covers BN only and would need (a) for the
          field code anyway.
    Not checked: other libgcc helpers that the crypto code may call on these cores
    (64-bit shifts are inline; the 64-bit divide is only used in public paths).

Not affected by either: SSFCryptCTMemEq, SSFPoly1305Mac, SSFBNAdd / Sub / ModAdd / ModSub
/ IsZero / IsOne, SSFFE25519Reduce / ToBytes pass on every core and both compilers. (The
ssfec.c:1208 ternary compiles branch-free on every M3 / M4 / M33 build; on M0+ / M23 the
comb cases fail through C1 / C2 anyway, and the source fix stays in the plan.)

Limits: control flow only; only the inputs tried; qemu is not a cycle model (operand-
dependent instruction timing, such as the M3's UMULL / UMLAL early termination, is not
seen).

STEPS 2-4 RESULTS (C1 FIXED)
----------------------------
Change:
  - ssfport.h: SSF_CT_VALUE_BARRIER(x). GCC / clang: __asm__("" : "+r"(x)), no instruction
    emitted. Others: a volatile round trip.
  - ssfcrypt.h: SSFCryptCTNonZero / IsZero / Eq / Lt (static inline, uint32_t, return 1 or
    0). No comparison operator, with a barrier on the intermediate whose top bit is the
    answer and another on the returned bit.
  - Every masked select in the constant-time paths builds its mask through a barrier:
      ssfbn: CondCopy, CondSwap, _SSFBNRawCmp (compares -> SSFCryptCTLt, a barriered
        "live" mask), ModAdd, ModSub, ModMulCT (shift-subtract), MontMul / MontSquare final

      ssfpoly1305 final select, ssfrsa _SSFRSAMod65537

        "(mask == 0u) ? 1u : 0u" -> SSFCryptCTIsZero
How it went (each round re-run on all 20 builds):
  1. Barrier on each finished mask: GCC all green, but clang M0+ / M23 still branched in
     CondCopy / CondSwap / MontMul. Clang computes the mask itself with a branch, before
     the barrier, by matching "(x | -x) >> 31" to "x != 0".
  2. Barrier moved inside the predicates, on the intermediate: CondCopy / CondSwap pass;
     ModAdd newly fails on clang, which turned "1 ^ (t >> 31)" into "t >= 0" and branched.
  3. Barrier also on each predicate's returned bit: 0 failures.
  4. Cost tuning: a barrier on a finished mask stops Thumb-2 folding the shift into the and
     ("and r, p, t, asr #31"). In the ModExp select that cost +278 K instructions on RSA-2048
     sign. Moving the barrier to just before the shift (select, divsteps) keeps the folding:
     +69 K. Re-checked: still 0 failures.

C2 IMPLEMENTATION PLAN
----------------------
Goal: on cores without a 32 x 32 -> 64 multiply (ARMv6-M: Cortex-M0 / M0+; ARMv8-M
Baseline: M23), no constant-time path calls libgcc's variable-time __aeabi_lmul / __muldi3.
Every other target must compile to the code it does today (byte-identical objects), so the
change costs nothing there.

Inventory: 64-bit products in _crypto, with whether their operands are secret.
  ssfbn       the row kernel (_SSF_BN_MAC's C branch: every Montgomery / schoolbook
              product), MontSquare's diagonal, the remaining (SSFBNDLimb_t)a * b sites
              (17 hits), and safegcd's int64 x int64 matrix products (_SSFBNS30UpdateFG /
              UpdateDE: int32-range operands, typed int64)                         secret
  ssffe25519  Mul (:61), the x38 fold (:72), bit x 19 (:127, :137)                  secret
  ssfx25519   :93 (2p x borrow, borrow 0 / 1), :112 (a x small constant)           secret
  ssfed25519  :62 (carry x 38); scalar arithmetic mod L in int64 byte limbs: the
              fold "(16 * x[i]) * L[j]" (:581), "q * L[j]" (:594), "carry * L[j]"
              (:600), the schoolbook "a[i] * b[j]" (:706)                          secret
  ssfpoly1305 the h x r block multiply (26-bit limbs, 15 hits)                     secret
  ssfaesgcm   GHASH's masked integer multiply (:110-117), on the hash key H and the
              data                                                                 secret
  ssfrsa      _SSFRSAMulMod65537 (:1109), :1155: keygen on secret prime candidates  secret
  ssfasn1, ssfaesccm, ssfsha1: lengths and encodings                               public
  Not multiplies, also seen as libgcc calls on M0+ (noted, not C2):
    __aeabi_llsl in _SSFBNToS30 / ModInvCT core: 64-bit shifts by public amounts.
    __aeabi_uidivmod / __aeabi_uldivmod in SSFBNGenPrime / SSFBNModUint32: trial division
      of SECRET prime candidates by small public primes. libgcc's divide is variable time;
      on M0+ / M23 (no UDIV) this leaks residues of the accepted primes. Open it as C3 and
      leave it out of C2.

Design:
  ssfcrypt.h, next to the C1 predicates:
    SSF_CT_MUL32(a, b)  -> uint64_t, unsigned 32 x 32 -> 64
    SSF_CT_SMUL32(a, b) -> int64_t, signed 32 x 32 -> 64
  On targets with a widening multiply (everything except __ARM_ARCH_6M__ /
  __ARM_ARCH_8M_BASE__), these expand to the plain C product, ((uint64_t)a * (uint64_t)b),
  so the generated code is unchanged. On ARMv6-M / v8-M Baseline they call static inline
  helpers:
    SSFCryptCTMul32(a, b): four 32-bit MULS on 16-bit halves, assembled without any carry
      compare. Let lo = al*bl, m1 = al*bh, m2 = ah*bl, hi = ah*bh. Then
      t = (lo >> 16) + (m1 & 0xFFFF) + (m2 & 0xFFFF), which is < 3 * 2^16 and cannot
      overflow, and
        result_lo = (lo & 0xFFFF) | (t << 16)
        result_hi = hi + (m1 >> 16) + (m2 >> 16) + (t >> 16)
      No branch, so nothing for a compiler to turn into one. About 4 MULS + 12 ALU against
      __aeabi_lmul's call and its 64 x 64 work (R7 measured a 16-bit-halves C kernel at
      -12.1% on M0+ RSA sign, so likely a speed gain).
    SSFCryptCTSMul32(a, b): the unsigned product minus (b if a < 0) << 32 and minus
      (a if b < 0) << 32, with sign masks from arithmetic shifts through
      SSF_CT_VALUE_BARRIER (C1's rule).
  Every inventory site gets the macro. Additions of the products stay 64-bit C: on ARMv6-M
  those compile to adds / adcs, inline and constant time.
  Sites whose operands are typed int64 but are bounded to int32 (safegcd matrix x limb,
  Ed25519 byte-limb scalar arithmetic) get a range comment and, under unit test, an
  assert that the operand fits. Each bound is worked out from the code before converting,
  and recorded here. Any site that cannot be bounded is reported, not guessed.
  Constant multipliers (x 19, x 38, x 65537, x 2p): use the macro too. Step 1 checks
  whether GCC / clang already inline these on ARMv6-M; converting them anyway costs nothing
  where they already do.

C3. Trial division of secret prime candidates uses a variable-time divide            OPEN
    SSFBNGenPrime's trial division (SSFBNModUint32 and the 16-bit-step remainder) runs
    "%" / "/" on the secret candidate. On Cortex-M0 / M0+ / M23 (no divide instruction)
    that is libgcc's __aeabi_uidivmod / __aeabi_uldivmod, which loops and branches on the
    operands. Rejected candidates are discarded, but the accepted primes p and q pass
    through it too, and their residues mod the small primes are what leaks. Cortex-M3 / M4
    / M33 have UDIV, whose cycle count also depends on the operands (early termination);
    qemu cannot see that.
    Fix direction (planned after C2): a remainder with no divide at all. For each small
    public prime d, a precomputed reciprocal and a multiply-shift with one masked
    correction; with C2's SSF_CT_MUL32 on ARMv6-M. That fixes every core, UDIV ones
    included.
